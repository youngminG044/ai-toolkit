# 업무 결과물 이해와 담당자 인계

실제 파일과 실행 결과를 읽고 입력→주요 처리→출력 흐름, 핵심 함수/파일, 중요한 선택, 검증 근거, 한계를 연결한다. 의도한 구조와 구현된 구조가 다르면 차이를 밝힌다.

먼저 probe의 페르소나·페인포인트·원인/근거·해결 원리를 짧게 읽고 해당 기능과 연결한다. 누가 어떤 문제 때문에 이 코드를 쓰는지, 무엇이 확인된 원인이고 가설인지, 기능이 원인 또는 증상에 어떻게 작용하는지 설명한다. 기술 테스트 통과와 실제 업무 개선 효과를 구분한다.

## 사용 장면부터 구조와 이유까지

사용자가 하려는 행동과 화면/파일에 나타나는 결과부터 설명하고, 그 경로의 데이터 흐름·모듈 책임·핵심 규칙·선택 이유·예외로 깊이를 늘린다. 기술 이름과 파일 목록만 나열하지 않는다. 여러 부분의 연결이 이해에 도움이 되면 작은 다이어그램에 구성 요소를 순서대로 더하며 설명한다.

SERVICE.md가 있으면 현재 컴포넌트 관계·아키텍처/대표 흐름 다이어그램·API 명세·업무/운영 규칙·근거·검증/효과를 실제 코드와 대조해 설명한다. 사용자 행동 하나가 어떤 컴포넌트·규칙·API/출력과 연결되는지 따라가고, probe.md의 기술 선택/대안과 devlog.md의 사건으로 이어준다. 서비스 설명을 업무 README에 덧붙이지 않는다. 문서나 그림만으로 사용자 이해 완료라고 하지 않는다.

구현 전 설명은 계획과 제안임을 밝히고 예상 결과물·사용 흐름·기능·구조·기술/대안·위험/검증·시간을 상세히 제시한 뒤 사용자 확인을 기다린다. solve-task가 사용 가능하면 그 스킬의 `references/implementation-brief.md`를 읽는다. 인계 설명은 실제 코드·실행 근거를 읽어 승인된 계획→현재 구현→검증 결과와 달라진 점을 연결한다. 코드를 읽지 않고 의도만 설명하거나 계획상의 파일/기능을 이미 존재하는 것으로 소개하지 않는다. 이유의 근거가 없으면 가설/미확인으로 둔다.

## 사용자가 코드를 읽는 시간

사용자는 코드를 읽는 경험이 없다는 전제로 설명한다. 변수/타입·함수/반환값·분기/반복·상태·await를 처음 만날 때 쉬운 한국어와 작은 입력의 실제 값으로 풀어준다. SERVICE.md의 유스케이스→화면/서버 라우팅→모듈 계약→대표 호출 흐름→읽는 순서/용어표를 사용한다. 라이브러리 이름·폴더 목록만으로 설명을 마치지 않는다.

구현·보완 시간에는 실제 파일/핵심 함수에 호출자·입력과 단위·출력·업무 규칙/이유·부작용/실패를 상세 주석으로 남긴다. 복잡한 분기/반복/수식/비동기 상태를 블록별로 설명하고 필요한 구문은 줄 단위로 보완한다. build-service가 있으면 그 스킬의 `references/code-understanding.md`를 따른다. 마지막 이해 시간에는 주석 추가도 자동 수행하지 않고 이미 준비한 주석과 현재 코드로 설명한다.

업무 범위와 합의한 일정에 사용자 코드 이해·담당자 검토·직접 검증 시간을 포함한다. 인계 시 `probe.md`의 기능 목록, SERVICE.md의 구조/계약, 현재 diff를 안내한다. 사용자가 읽는 파일을 알리지 않고 수정하거나 새 기능을 추가하지 않는다. 요청된 설명과 사용자가 직접 예측·읽기·실행·설명할 시간을 함께 제공한다.

기본 180분 집중 세션에서 첫 60분은 1차 구현·대표 검증, 다음 60분은 보완/수정과 이해 병행, 마지막 60분(T+120~180분)은 온전히 코드 이해에 쓴다. 1차 인계가 T+80분으로 늦어져도 마지막 구간은 이동하지 않는다. T+120분 이후에는 새 기능·리팩터링·자동 오류 수정·문서 확장·새 장시간 검증 대신 현재 코드와 준비된 SERVICE/probe/devlog를 읽고 설명한다. 사용자가 직접 입력 결과를 예측하고 구성 요소→함수→규칙→출력을 추적하도록 지원한다. 발견한 문제는 수정 후보로 남기며 명시 수정 요청이 있을 때만 시간 영향을 밝히고 요청 범위를 수행한다.

기능 하나씩 다음을 진행한다.

1. 작은 입력의 결과를 사용자가 먼저 예측한다.
2. 관련 진입점→핵심 함수→출력을 실제 코드에서 추적한다.
3. probe.md의 선택안·대안·장단점·결론을 읽고 현재 제약에서의 의미를 설명한다.
4. 대표 사례와 경계/실패 사례의 테스트 코드·결과를 함께 읽는다. 무엇을 왜 검사했는지, 준비 입력→호출→기대값과 비교하는 assert가 무엇인지 쉬운 말로 설명하고 실제 결과·판정·미확인을 대조한다. 허용된 시간/환경에서는 직접 실행이나 수동 계산으로 확인한다. 예상한 입력 오류의 거절이 테스트 통과인 경우와 검사 자체의 실패를 구분한다.
5. 본인이 선택 이유·검증·한계를 말한다. 답과 코드가 다르면 해당 지점만 다시 확인한다.

probe.md의 사용자 이해 상태는 실제 확인한 범위만 갱신하고, devlog.md에는 질문·직접 실행·확인한 사실과 남은 부분을 짧게 남긴다. AI가 설명문을 만든 것만으로 사용자 이해 완료라고 쓰지 않는다. 필요한 경우 `record-work`의 문서 기준을 읽는다.

설명은 다음 연결을 중심으로 한다.

- 문제와 사용자 결정 → 선택한 범위.
- 비교한 대안 → 현재 선택의 이유와 포기한 점.
- 중요한 규칙 → 구현 위치와 작은 예시.
- 주장하는 결과 → 실제 검증·표본·실행 조건.
- 실패 조건 → 현재 처리와 남은 개선.
- 강제 조건과 선호 기준 → 실제 식/판정 순서 → 대안에서 얻거나 잃는 점. 최적화 기능이 있을 때만 해당 내용을 설명한다.
- 백그라운드 실행 → 실제 작업 상태/저장 위치 → 중복 요청·실패·재시작 결과. `await`와 영속 작업 큐를 구분한다.
- 설정·수요 분포 변화 → 예상 영향 → 관측 지표/실제 결과 또는 다음 검증.
- AI 원인 가설/수정 제안 → 채택·수정 요청·기각 → 사용자 본인의 근거와 재확인. 실제 기록이 없으면 확인 전으로 둔다.

사용자가 함께 이해를 확인하고 싶다고 요청하면 한 번에 핵심 질문 하나를 다룬다. 사용자 설명과 실제 구현을 대조해 다른 부분·남은 질문을 짚고 다음 확인으로 이어간다. 결정·실험·담당자 동의는 실제로 확인한 근거로 설명한다.

담당자와 확인할 핵심 질문은 “이 입력은 어디서 어떻게 처리되나?”, “왜 이 대안을 택했나?”, “어떤 근거로 업무 규칙을 충족했음을 확인했나?”, “운영 조건이 바뀌면 무엇을 다시 확인해야 하나?”다.

현재 프로젝트의 자료 접근·기밀 유지·AI 도구 사용 정책을 따른다. 실제로 확인하지 않은 담당자 동의·사용자 이해·운영 효과를 만들어 쓰지 않는다.
