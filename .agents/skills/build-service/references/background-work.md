# 비동기·백그라운드 작업의 약속

오래 걸리는 계산·외부 요청·재계산을 다룰 때 읽는다. 업무에 필요하지 않은 큐·캐시·워커를 자동 추가하지 않는다.

## 서로 다른 개념

- `async/await`: 대기 후 이어서 실행하는 제어 방식. 계산의 병렬화·백그라운드 분리·중단 후 복구를 저절로 제공하지 않는다.
- 호출 스택: 현재 실행 중인 함수들이 돌아갈 위치를 쌓는 구조. 작업 보관소를 선택할 때 큐와 스택 중 하나를 반드시 골라야 하는 것은 아니다.
- 작업 큐: 실행 대기 작업을 보관·전달하는 장치. 순서·우선순위·저장·재전달 정책은 구현에 따라 다르다. 브라우저 이벤트 루프의 큐와 서버의 영속 작업 큐를 혼동하지 않는다.
- 워커: 작업을 실제 수행하는 실행 주체. 별도 프로세스인지, 서버 안의 스레드/태스크인지, 누가 시작/종료하는지 확인한다.

[FastAPI 공식 안내](https://fastapi.tiangolo.com/tutorial/background-tasks/)는 응답 이후 작업과 무거운 계산을 위한 별도 도구의 용도를 구분한다. 현재 환경의 버전과 실제 코드를 우선한다.

## 구현 전에 설명할 결정

| 결정 | 확인하고 합의할 내용 |
| --- | --- |
| 실행 위치 | 요청 안에서 완료 / 같은 서버의 백그라운드 작업 / 별도 워커. 처리 시간·CPU/I/O·동시 사용자·설치 조건으로 선택 |
| 중복 요청 | 거절 / 같은 작업 ID 반환 / 대기열 / 이전 작업 취소 중 실제 정책. 다른 사용자·다른 입력의 처리도 구분 |
| 상태·식별 | 실제 상태 목록, 작업 ID, 생성/시작/완료 시각, 상태/결과 조회 방법, 실패를 UI가 인지하는 경로 |
| 입력 일관성 | 실행 시점의 입력·설정 버전 고정 여부, 계산 중 변경, 오래된 작업의 늦은 결과가 최신 결과를 덮는지 |
| 결과 게시 | 계산 중 이전 정상 결과 조회 가능 여부, 검증 완료 후 한 번에 교체하는지, 일부 결과 노출 여부 |
| 실패·시간 초과 | 오류 기록·사용자 안내·이전 결과 보존·자동/수동 재시도·재시도 한도 |
| 재시작·복구 | 작업과 상태를 메모리/DB/큐 어디에 저장하는가. 실행 중 작업 탐지, 실패/중단 표시 또는 재실행 방식 |
| 자원·범위 | 동시 실행/대기 한도, 데이터 크기, 잠금 범위, 여러 프로세스/서버에서 동작하는지 |

동일 브라우저의 버튼 비활성화는 서버의 중복 요청 방지가 아니다. 메모리 잠금은 여러 프로세스를 보호하지 않으며, DB에 상태만 저장했다고 실행 중 작업이 자동 재개되지는 않는다. 큐를 사용해도 중복 실행·재시도·결과 교체의 올바름을 별도로 설계한다.

## 가장 단순한 충분한 방식 선택

짧고 작은 작업이면 동기 응답으로 충분할 수 있다. 응답 후 소규모 작업은 같은 프로세스에서 처리할 수 있지만 강제 종료 시 유실될 수 있음을 설명한다. 재시작 복구·많은 요청·무거운 CPU 계산이 실제 요구라면 영속 작업 저장·별도 실행 주체를 비교한다. Redis/Celery 등의 추가 운영 비용도 대안에 포함하고 사용자가 승인한 구조 안에서 구현한다.

## 확인과 기록

SERVICE.md에 실제 상태 전이와 요청→접수→계산→검증→결과 게시→조회 흐름, 위 결정 표의 현재 구현·미구현을 적는다. 대표 정상, 동시 요청, 계산 예외, 입력 변경, 실행 주체 중단/재시작 중 중요한 사례를 통제된 허용 환경에서 확인한다. 실제 공유 서버·플랫폼을 중단하지 않는다.

각 사례의 기대 상태/HTTP 응답/결과 보존 여부와 관측 결과를 남긴다. 실행하지 못한 재시작·부하 검사는 NOT_RUN이다. `202` 응답·로딩 UI·`async` 선언만으로 백그라운드 신뢰성 검증을 완료하지 않는다.
