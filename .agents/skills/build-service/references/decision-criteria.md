# 결과를 선택하는 기준과 조건 변화

최적화·추천·점수·분류·우선순위 결정이 실제 기능에 있을 때 읽는다. 알고리즘 이름보다 업무 목적과 현재 코드의 판정 순서를 설명한다.

## 먼저 합의하고 구현할 것

- **반드시 지킬 조건**과 **유효한 결과들 중 더 좋은 것을 고르는 기준**을 분리한다. 위반을 허용하지 않는 조건을 작은 가중치로 손쉽게 상쇄하지 않는다. 조건을 만족하는 해가 없을 때의 응답과 운영자 행동도 합의한다.
- 여러 목표가 충돌하면 우선순위 비교, 가중합, 단계별 최적화 등 실제 적용할 방식을 브리핑한다. 지표의 단위·합/평균/최대·분모·정규화·가중치의 근거와 동점 처리를 명시한다. 담당자 확인이 없으면 확인 대기로 남긴다.
- 현재 코드가 실제로 사용하는 식·비교 조건·단계별 휴리스틱을 확인한다. 모든 목표를 하나의 수식으로 최적화한다고 가정하지 않는다. 근사·탐욕적 선택이라면 전역 최적 보장이 없는 점을 밝힌다.

## 남길 근거

probe.md에 `업무 목표 → 강제 조건/선호 기준 → 실제 식·우선순위와 코드 위치 → 선택 이유 → 얻은 점/포기한 점`을 기록한다. 미사용 대안과 비교는 설계상 예상인지 동일 입력의 실제 실행 비교인지 구분한다. 기준을 사후에 보기 좋게 만들어 현재 코드의 의도라고 쓰지 않는다.

SERVICE.md에는 각 처리 단계의 입력·출력·규칙·실패·다음 단계 계약을 적는다. 생성기가 만든 결과를 생성기와 독립적으로 검사할 규칙과 기대값도 연결한다. 같은 잘못된 함수로 생성과 정답 계산을 함께 하면 통과해도 그 규칙은 확인되지 않을 수 있다.

## 민감도 확인

업무에서 중요한 설정 1~2개와 수요 분포 변화 한 가지를 고른다. 기준 입력을 고정하고 조건 하나씩 바꿔 유효 결과 존재 여부, 위반 건수, 목적 지표, 최대/상위 구간 지표, 미처리 수, 실행 시간을 비교한다. 자원이 모자라는 극단값·단일 집단 집중·빈 데이터처럼 실제 요구와 관련 있는 사례를 포함한다.

변화 방향은 가설로 먼저 쓰고 실제 결과와 대조한다. 휴리스틱 결과가 조건 변화에 항상 단조롭게 반응한다고 보장하지 않는다. 미측정 성능·품질은 추정으로 표시한다. 가장 큰 사용자 피해가 생기는 실패 조건을 골라 다음 입력·지표·기대 결과까지 제안한다.
