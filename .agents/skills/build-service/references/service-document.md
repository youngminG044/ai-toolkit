# SERVICE.md — 구현 서비스의 기술 설명서

사용자가 업무 설명과 구현 설명을 따로 읽을 수 있게 **실제 업무 폴더의 SERVICE.md**를 생성·유지한다. 업무 설명이 있는 README.md/readme.md의 내용을 수정·교체하거나 생성한 서비스 설명을 덧붙이지 않는다. 기존 사용자 SERVICE.md는 보존하며 필요한 구획만 보완한다. 같은 이름의 파일이 다른 용도이거나 심볼릭 링크/디렉터리이면 덮어쓰지 않고 충돌을 알린다. 별도 위치가 필요하면 실제 위치를 사용자에게 안내한다.

## 작성 시점과 문서 역할

- 구현 전 브리핑·계획 확인은 probe.md에서 관리한다. 서비스 구현에 들어가면 SERVICE.md를 준비하고 실제로 확인한 코드·규칙·실행 결과를 반영한다. 설치만으로 완성된 서비스 문서가 있다고 주장하지 않는다.
- [기본 양식](../assets/SERVICE.template.md)을 참고한다. 없는 경우에만 새 파일을 만들고, 기존 내용은 무조건 복사로 교체하지 않는다. 양식을 그대로 둔 상태는 작성 준비다.
- SERVICE.md는 현재 구조·상세 계약·운영 안내의 정본, probe.md는 문제/선택 이유·대안/장단점·검증 핵심의 정본, devlog.md는 실제 사건 이력이다. 같은 기능 ID와 확인한 실제 경로로 연결하며 긴 내용을 세 번 복제하지 않는다. 두 기록 문서에서도 핵심 구조·동작·근거를 찾을 수 있게 요약과 링크를 유지한다.
- 필수 RUN.md 등은 그대로 충족하고 상세 실행 절차를 연결한다. 추가 문서가 금지되면 허용된 문서와 위치를 먼저 확인하고 그 구획으로 통합한다. 업무 README에 임의로 합치는 것을 기본 대안으로 삼지 않는다.

## 필수 내용

### 서비스 목적과 사용 흐름

누가 무엇을 입력하고 어떤 결과를 받아 어떤 결정을 하는지 설명한다. 실제 구현·미구현·계획을 구분하고 업무 요구·담당자 답변·합의한 브리핑과 연결한다. 화면별 핵심 동작과 입력→처리→출력의 대표 경로를 먼저 제시한다.

사용자 목표별 유스케이스의 선행 조건·정상 단계·대체/실패 흐름·완료 조건을 작성한다. 유저플로우는 사용자가 경험하는 순서, 아키텍처는 구성 요소의 관계, 호출 흐름은 코드가 실행되는 순서임을 구분해 설명한다.

### 컴포넌트 관계와 아키텍처 다이어그램

실제 컴포넌트/모듈마다 역할·코드 위치·입력·출력·연결 대상·상태/데이터 소유자를 적는다. 프런트는 부모/자식·props/callback·공유 상태·라우팅, 서버/분석은 호출·저장·외부 의존성을 해당되는 만큼 설명한다.

현재 코드를 근거로 전체 구성과 통신/데이터 방향을 보여주는 Mermaid 아키텍처 다이어그램을 작성한다. 대표 사용자 동작이 여러 부분을 오가면 시퀀스 또는 데이터 흐름 다이어그램도 작성한다. 연결선에는 무엇이 오가는지 표시하고 실제 코드 위치와 대조한다. 렌더링이 안 되는 환경에서도 이해할 수 있도록 관계 표와 짧은 텍스트 흐름을 함께 둔다. 사용하지 않은 DB·AI 모델·외부 서비스를 그리지 않으며, 계획 노드는 구현된 노드와 분리해 표시한다.

[처음 읽는 사람을 위한 기준](code-understanding.md)을 적용해 화면 URL/내부 탭→컴포넌트와 HTTP 메서드/URL→처리 함수의 라우팅을 구분한다. 실제 모듈/핵심 함수의 호출자·입력/단위·반환값·부작용·실패와 단계별 중간 데이터가 다음 단계로 전달되는 계약을 적는다. 대표 입력을 따라 읽을 `파일:심볼` 순서와 쉬운 용어표도 유지한다. 함수 이름만 나열하지 않는다.

### API 명세

실제 API를 메서드·경로·목적·관련 기능·입력(query/path/body)·성공 응답·주요 오류·인증/권한·코드 위치로 정리한다. 중요한 요청/응답 필드는 타입·필수 여부·단위·제약을 적고 합성 예시를 제공한다. 실제 라우트·OpenAPI·직접 확인한 응답을 대조하고, 응답 스키마가 불완전하거나 미검증이면 그 상태를 밝힌다.

문서/스키마 URL과 공개 여부는 별도로 적는다. Markdown API 명세 작성을 이유로 익명 접근·Swagger 공개·새 외부 배포를 활성화하지 않는다. API 없는 정적/프런트 전용 서비스는 해당 없음과 실제 연결 방식을 적으며 문서용 백엔드를 만들지 않는다.

### 업무 규칙과 운영 규칙

업무 규칙은 임계값·정렬/필터·분모/집계·결측/중복·상태 전이·예외 등 결과를 바꾸는 기준을 정리한다. 규칙→요구/담당자 답변 근거→구현 위치→검증 사례를 연결하고 근거 없는 정책을 만들어 쓰지 않는다.

선택/최적화가 있으면 [판정 기준](decision-criteria.md)에 따라 강제 조건과 선호 목표, 실제 식/우선순위·단위·가중치 근거·조건을 만족하는 해가 없을 때의 처리·전역 최적 보장 여부를 설명한다. 생성과 규칙 검사의 호출/의존 관계, 공용 로직 범위와 독립 기대값을 밝힌다. 같은 로직을 재실행해 같은 결과를 얻는 것과 규칙을 독립 확인하는 것을 구분한다.

운영 규칙은 실행/종료·필수 의존성·설정·입력/저장·재시작/갱신·실패 시 동작·상태 URL의 검사 범위·접근 권한·문서 공개·현재 복구 한계를 실제 구현 범위에서 적는다. 설정 키는 설명하되 비밀 값·개인정보·원시 민감 로그를 문서에 복사하지 않는다. 운영 절차를 실제로 실행했는지 구분한다.

백그라운드 작업이 있으면 [작업 수명 기준](background-work.md)의 상태 전이, 중복/동시 요청, 입력 버전, 결과 게시, 실패·시간 초과·재시작/복구 정책을 표로 적는다. 없으면 해당 없음으로 둔다. [전체화면 유지 기준](fullscreen-compatibility.md)이 적용되면 사용자 동작별 앱 코드 점검 결과와 실제 환경 확인 대기/관측을 구분한다.

### 근거·검증·효과·한계

요구/기능→컴포넌트/코드→규칙과 출처→API/출력→검증 사례→효과/한계를 한 표로 연결한다. 기존 PR/F 등 ID를 재사용하며 작은 프로젝트에 불필요한 번호 체계를 늘리지 않는다.

검증은 입력/조건·독립된 기대값·명령/절차·실제 결과·상태·관련 버전/변경 상태·근거 위치를 기록한다. 정상·경계·실패와 사용자 직접 확인을 구분하며, 문서/상태 URL 200을 업무 검증 완료로 쓰지 않는다. 원시 로그는 필요한 위치만 연결한다.

무엇을 왜 검사하는지 업무 규칙/사용자 영향으로 설명하고 실제 테스트 파일:함수/케이스와 연결한다. 실행 전 목적·입력/기대값을 짧게 알리고, 실행 후 기대/실제값·판정·한계/다음 조치를 사용자용 표로 보여준다. 케이스의 준비 데이터·호출·assert와 출력을 직접 읽어 해석하며 통과 개수·종료 코드만으로 설명을 끝내지 않는다. 현재 업무 테스트의 목적별 목록을 유지하고 많은 사례는 같은 문서의 상세 목록으로 연결한다. 확인 가능한 실행/통과/실패/생략 집계만 적고 중복 실행을 합산하지 않는다. verify-result가 있으면 해당 스킬의 `references/test-explanation.md`를 따른다.

조건 변화는 기준 입력·바꾼 설정/분포·예상 영향·실제 지표·결과와 남는 위험을 연결한다. 독립 검사기의 반례, 관련 있는 동시/실패/재시작 사례, 전체화면 관련 UI 점검을 구분하고 실행하지 못한 항목을 채워 넣지 않는다.

효과는 기대 효과, 기술 동작으로 확인한 결과, 실제 업무 측정 결과를 나눠 적는다. 업무 기준값/목표값·측정 조건/표본·실제 결과가 없으면 미측정으로 둔다. 처리 속도·누락 감소·시간 절감 수치를 만들지 않는다. 미구현/미검증·사용자 영향·개선 우선순위·다음 확인 방법을 연결한다.

## 갱신과 인계

구조·API·규칙·실행 설정·검증 결과가 바뀌면 영향받는 SERVICE.md 구획을 같은 작업에서 갱신한다. 인계 전에 실제 코드와 다이어그램 노드/연결, API 목록/필드, 규칙/근거, 실행 정보, 검증·효과 주장을 대조한다. probe.md에는 핵심 요약과 상세 위치, devlog.md에는 변경·검사 사건을 남긴다. 문서 존재나 다이어그램 작성 자체를 구현·검증·사용자 이해 완료로 표시하지 않는다.
