# 처음 코드를 읽는 사람에게 인계하기

사용자는 코드를 읽는 경험이 없으므로 실제 업무 코드에 상세한 한국어 설명 주석을 작성한다. 구현과 함께 준비하고 기본 집중 세션의 T+120분 전에 정합을 마친다. 마지막 이해 시간에 새 설명 파일·코드를 대량 작성하지 않는다.

## 연결해서 보여줄 구조

SERVICE.md에 다음을 실제 경로·심볼 이름과 연결한다. 없는 구성 요소는 해당 없음으로 둔다.

- 아키텍처: 화면·서버·계산·검증·저장 구성 요소, 각 책임과 데이터 방향.
- 사용자 흐름: 사용자가 어떤 화면에서 무엇을 입력하고 어떤 상태/결과를 보는가.
- 유스케이스: 사용자 목표, 선행 조건, 정상 단계, 빈 입력/실패/중복 요청의 대체 흐름, 완료 조건.
- 라우팅: 화면 URL 또는 내부 탭 → 컴포넌트, HTTP 메서드/URL → 서버 처리 함수. 화면 전환과 API 요청은 다르며 내부 탭만 있으면 URL 라우터를 사용한다고 쓰지 않는다.
- 모듈 계약: 누가 호출하는가, 입력 필드/단위, 반환값, 다음 호출 대상, 변경하는 상태/DB, 오류가 전달되는 위치.
- 대표 입력 한 건: UI 이벤트 → API 호출 → 서버 진입점 → 업무 함수/분기 → 검증/저장 → 응답 → 화면 표시. 실제 순서를 쓰고, 핵심 중간 데이터의 작은 합성 예시를 붙인다.

다이어그램에 실제 없는 큐·DB·AI 모델을 추가하지 않는다. 비동기 작업이 있으면 계산 완료 전 HTTP 응답이 돌아가는 지점과 결과를 다시 조회하는 경로를 분리한다.

## 주석의 구체적 기준

1. 파일 머리에 업무상 역할, 들어오는 곳/나가는 곳, 읽을 순서를 적는다. 원래 라이선스·필수 지시 주석은 보존한다.
2. 핵심 함수/컴포넌트에는 호출자, 입력·타입·단위·예시, 반환값, 업무 규칙과 이유, 저장/네트워크 부작용, 오류/한계를 설명한다.
3. 업무를 바꾸는 분기·반복·집계·정렬·목적함수·시간 계산·비동기 상태 전이에 블록 주석을 단다. 예: 왜 이 사람을 제외하는지, 비교 기호의 등호가 포함되는지, 분과 초를 어디서 변환하는지, 실패 시 기존 결과가 유지되는지.
4. `state`는 화면이 기억하는 값, `await`는 결과를 기다린 뒤 이어서 실행하는 지점처럼 첫 등장 문법을 쉬운 말로 설명한다. 전문 용어는 SERVICE.md의 짧은 용어표에 연결한다. 식이 복잡하면 변수 의미와 작은 계산 예를 먼저 적는다.
5. 사용자가 막히는 구문은 줄 단위로 추가 설명한다. 핵심 경로의 설명을 생략한 채 ‘자명한 코드’라고 판단하지 않는다. 동작·선택 이유·실패 조건을 주석으로 이해할 수 있어야 한다.
6. 주석은 현재 코드의 사실을 설명한다. `async`만 보고 병렬 실행·재시작 복구를 보장한다고 쓰지 않는다. 가정·미측정·계획을 구분하고 구현 변경 시 함께 고친다.

## 읽고 설명할 수 있는 인계

SERVICE.md에 `순서 | 파일:심볼 | 담당 동작 | 읽고 답할 질문` 표를 둔다. probe.md에는 기능별 핵심 흐름·선택 이유·검증 근거를 요약하고 상세 위치를 연결한다. 사용자는 대표 입력의 결과를 먼저 예상하고, 주석을 따라 현재 값을 추적한 뒤 자신의 말로 설명한다. 설명문·주석의 존재만으로 사용자 이해 완료를 기록하지 않는다.
