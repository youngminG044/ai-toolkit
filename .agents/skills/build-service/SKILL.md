# 작동하는 서비스 구현

## 구현 전

- 상세 구현 브리핑과 사용자 확인이 현재 범위에 대해 완료됐는지 확인한다. 직접 호출됐더라도 확인되지 않은 새 업무는 답변 반영·예상 화면/사용 흐름·기능별 입출력/예외·범위·데이터/구조·기술/대안·위험/검증·시간을 채팅에 자세히 설명하고 사용자 확인을 기다린다. 확인 전에는 업무 코드·뼈대 복사를 시작하지 않는다. 이미 합의한 범위의 통상 구현·오류 수정은 반복 확인하지 않는다. solve-task가 사용 가능하면 그 스킬의 `references/implementation-brief.md`를 상세 기준으로 읽고, 선택 설치로 없더라도 이 확인 절차는 유지한다.
- 실제 실행 명령·의존성·기존 구조·데이터 계약을 확인한다. 이미 작동하는 스택을 보존한다.
- 새 구현·수정을 시작하기 전 예상 소요 범위(구현·검증·기록 포함), 근거/미확인 조건, 현재 인계 목표에 주는 영향을 짧게 알린다. 첫 실행이나 오류·범위 변경으로 추정이 달라지면 남은 시간을 갱신한다. 시간 안내 때문에 이미 승인된 통상 작업의 시작 승인을 다시 요구하지 않는다.
- 새 앱의 실행형 코드가 필요하면 [뼈대 선택](references/starter-selection.md)을 읽는다. React·FastAPI·SQLite·RAG·CSV/ML·Docker 모듈을 필요한 조합으로 사용하고, 기본 예시를 실제 요구로 바꾼다.
- 개발 서버가 아니라 결과물을 받는 사람의 사용 조건으로 형태를 결정한다. 설치·서버 실행이 불가능한 사용자에게 서버형 앱을 임의로 전달하지 않는다. 저장·협업 요구와 사용 조건이 충돌하면 담당자에게 확인하고, 가능한 형태를 probe.md의 선택안/대안으로 비교한다.
- 사용자 핵심 동작 하나를 입력→처리→출력/저장으로 추적한다. 필수 화면과 선택 화면을 구분한다.
- 합의한 담당자 질의·답변 단계가 있으면 그 답변과 사용자 결정을 반영한 뒤 구현한다. probe의 페르소나→페인포인트→원인/근거→해결 원리와 기능을 연결하고, 중요한 업무 정책이 미확인이면 해당 로직은 사용자 판단 전 확정하지 않는다.
- 계산·판정·집계는 확인 가능한 함수로 분리한다. 데이터나 숫자를 시연용 상수로 바꾸지 않는다.
- 최적화·추천·점수 결정이 있으면 [판정 기준과 조건 변화](references/decision-criteria.md)를 읽고 강제 조건/선호 목표, 실제 식·우선순위, 단위·근거, 얻는 점/포기하는 점을 브리핑한다. 배경 계산을 쓰려면 [작업 수명과 실패 정책](references/background-work.md)을 읽고 중복 요청·결과 교체·실패·재시작 동작을 먼저 설명한다. 필요 없는 큐/워커를 추가하지 않는다.
- 전체화면 유지가 필요한 환경에서는 [전체화면 호환 기준](references/fullscreen-compatibility.md)을 수용 조건에 넣는다. 기본 UI는 페이지 내부에서 동작하며 새 창·네이티브 대화상자·다운로드·전체화면 API 호출을 피한다. 실제 IDE에서의 유지 여부는 별도 확인하고 감독 동작/로그를 변경하지 않는다.

## 구현 순서

1. 실행 가능한 최소 경로를 만든 뒤 바로 실행한다. 화면과 API를 따로 완성한 뒤 마지막에 연결하지 않는다.
2. 요청/응답 계약을 명확히 하고 정상·빈 결과·잘못된 입력·서버 오류 상태를 구현한다. 로딩 표시가 필요한 동작에는 완료/실패 상태를 둔다.
3. 요구된 저장이 실제 재조회·새로고침 후에도 유지되는지 확인한다. 데모 데이터는 합성이라고 표시하고 실제 데이터와 구분한다.
4. 좁은 화면·긴 텍스트·빈 목록·중복 클릭을 점검한다. 폼에는 라벨, 결과에는 단위·기간·분모를 표시한다. 버튼을 실제 결과와 연결한다.
5. 사용자 입력을 명령·HTML·SQL로 그대로 실행하지 않는다. 인증·권한이 필요한 업무면 서버에서도 권한을 검사하고 키는 클라이언트에 넣지 않는다.
6. 핵심 경로와 중요한 실패에 대해 기존 테스트 도구로 검증한다. 무엇을 왜 검사하는지 먼저 알리고, 실행 뒤 목적·입력·기대/실제 결과·판정·한계를 쉬운 말로 설명한다. 새로 작성/변경한 핵심 테스트에 준비→실행→비교와 기대값의 이유를 한국어로 설명한다. verify-result가 있으면 그 스킬의 `references/test-explanation.md`를 따른다. UI의 육안·클릭 확인은 사용자가 플랫폼 내 Browser에서 직접 수행할 절차를 적는다.
7. [초보자를 위한 코드와 읽는 지도](references/code-understanding.md)에 따라 파일·핵심 함수·분기/계산·비동기 상태에 상세한 한국어 주석을 쓴다. 실제 호출자·입력/단위·출력·업무상 이유·예외를 설명하고 구현 변경과 함께 갱신한다. 핵심 경로의 문법도 사용자가 이해할 수 있게 설명한다.

서비스 구현을 시작하면 별도 요청 없이 [SERVICE.md 작성 기준과 양식](references/service-document.md)을 사용해 실제 업무 폴더의 서비스 기술 설명서를 생성·갱신한다. 업무 README.md/readme.md는 보존한다. 현재 컴포넌트 관계·Mermaid 아키텍처/대표 흐름·API 명세·업무/운영 규칙과 근거·검증·효과/한계를 설명하고 probe.md·devlog.md에 연결한다. 계획 확인 전에는 업무 구현을 시작하지 않으며 문서도 현재 구현과 계획을 구분한다.

SERVICE.md에는 실제 유스케이스·화면 라우팅과 API 라우팅·모듈 입출력 계약·단계별 중간 데이터·코드 읽는 순서도 유지한다. 선택 기준/독립 검증/조건 변화와 백그라운드 수명은 해당 기능이 있을 때 작성한다. 문서·주석이 존재한다고 사용자가 이해했거나 운영 신뢰성이 검증됐다고 하지 않는다.

서버/API가 있는 웹서비스에는 [상태 확인·API 안내·접속 정보](references/service-access.md)를 적용한다. 기존 상태 경로·인증·문서 공개 정책은 유지하고 실제 포트/경로와 검증 결과를 SERVICE.md에 기록한다. 프런트 전용 결과물에는 API 해당 없음과 실제 연결을 설명하고 안내용 API 서버를 새로 도입하지 않는다.

업무 범위·마감·현재 코드와 실행 조건을 근거로 첫 작동 경로와 대표 검증의 인계 시점을 제안한다. 담당자 검토·사용자 코드 이해와 직접 검증 시간을 함께 계획하고, 범위/일정이 달라지면 먼저 설명한다. 기능이 생기거나 기술 선택이 달라지면 `record-work`에 따라 devlog.md에 실제 변경을, probe.md에 기능별 도구·대안의 장단점·선택 이유·검증 근거를 갱신한다.

기본 180분 집중 세션에서는 T+60분에 1차 코드·대표 검증·읽을 자료를 인계한다(지연 시 T+80분 대안). 보완·추가 구현·리팩터링·회귀 검사와 문서 정합은 T+120분 전에 마친다. T+120~180분에는 코드 변경 없이 이해만 지원하며 발견한 오류를 자동 수정하지 않는다. 사용자가 이 구간의 수정을 명시하면 이해 시간 영향을 알리고 요청 범위만 수행한다. 다른 세션 기간은 현재 사용자 지시를 따른다.

## 실제 업무 환경에서 실행

- 로컬·컨테이너·웹 IDE·배포 환경과 실제 포트·바인딩·접근 범위를 확인한다. 웹 IDE/컨테이너에서 필요한 경우 `0.0.0.0`을 사용하며 사용자가 접근할 주소와 구분한다. 개발 서버를 유지할 터미널을 안내한다.
- 현재 환경의 브라우저/포트 미리보기 또는 합의한 접속 경로로 확인한다. 터널·외부 배포가 필요하면 접근 정책과 사용자 권한 범위를 먼저 확인한다.
- 환경에서 허용된 HTTP·단위·통합·브라우저 검증을 선택한다. 자동화 검사와 사용자의 수동 UI 확인, 실행하지 못한 검사를 구분한다.
- 연결 실패는 서버 로그→프로세스 유지→포트→바인딩→경로 순서로 좁힌다. 무관한 재설치를 반복하지 않는다.

React 등이 실제 스택일 때만 관련 최적화 자료를 검토한다. 필수 기능이 작동하기 전에 새로운 프레임워크·디자인 시스템·인증·외부 API를 추가하지 않는다.

반환: 실행 명령, 화면·상태·API 안내의 실제 포트/경로, 구현한 사용자 흐름, 실제 검증 근거, 수동 확인할 동작, 남은 한계.
