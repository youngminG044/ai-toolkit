# 문제 분석과 실행

주어진 업무를 만족하는 결과물을 만든다. 특정 도메인·기술·결과물 형식을 미리 정하지 않는다.

담당자와 협업해 실제 업무 문제를 해결하는 상황을 기본으로 한다. 현재 사용자·업무 목표·운영 맥락·수용 기준을 확인한다. 사용자가 지정한 기본 집중 세션은 180분(1차 구현 60분 + 보완/이해 60분 + 변경 없는 이해 60분)이며, 업무 전체의 총기간과 구분한다. 결과물은 담당자가 어떻게 사용하고 운영할 수 있는지, 어떤 근거로 검증됐고 어떤 효과/한계가 있는지 설명한다.

## 짧은 호출의 기본 동작

`$solve-task` 한 번 또는 “업무 시작해줘”로 시작한다. 긴 프롬프트나 자동저장 추가 설정을 요구하지 않는다. [담당자 질의와 구현 흐름](references/discovery-dialogue.md) 및 [자동 세션](references/automatic-session.md)을 읽는다. 현재 업무의 지침 확인 뒤 `scripts/session.py start`로 기록 준비·3분 간격 로컬 자동저장을 시작한다. 기본 순서는 **문제 입력 → 문제/페르소나 분석·담당자 질문 → 확인한 답변 반영 → 구현 전 상세 브리핑 → 사용자 계획 확인 → 구현·검증·인계**다. 업무 답변과 설계 확인은 별개다. 확인 전에는 업무 기능 코드나 뼈대를 작성·설치하지 않는다. 기록 갱신도 기본 작업에 포함하며 사용자의 설정·문서/접근 제한을 따른다.

## 먼저 확인

1. 현재 작업 경로, README, 기존 AGENTS.md, 필수 산출물, 실행 방법, 제공 파일을 확인한다. 큰 데이터는 일부와 스키마부터 본다.
2. 요청된 문제와 제안된 해결책을 분리한다. 페르소나의 역할·목표·상황, 현재 흐름, 페인포인트·손실, 원인과 그 근거, 바꿀 결정, 성공 기준을 연결한다. 근거 없는 인물 설정과 검증되지 않은 원인 단정은 하지 않는다.
3. 사실·가정·자료 간 충돌·미확인을 구분한다. 각 필수 요구에 근거 위치와 확인 방법을 붙인다.
4. 사용자가 업무 담당자에게 보낼 질문과 확인 이유·구현 영향을 우선순위로 제안한다. 기존 자료에 답이 있으면 다시 묻지 않는다. 목표, 비용 비대칭, 용어·단위, 예외, 운영 조건을 필요에 맞게 확인한다. 개선 목표는 확인 가능한 현재값·목표값·측정 위치로 연결하고 값이 없으면 미확인으로 둔다. 결과물을 실제 사용할 사람의 인터넷·설치·서버·저장 가능 여부를 개발 환경과 구분해 확인한다.
5. 사용자가 확인한 답변을 입력하면 사실·충돌·열린 질문과 수용 기준을 갱신하고 [구현 전 상세 브리핑](references/implementation-brief.md)을 준비한다. 예상 결과물·기능별 동작·데이터 흐름·설계/기술·대안·검증·시간을 채팅에 설명하고 사용자가 계획을 확인할 때까지 구현을 보류한다. 대기 중에는 읽기 전용 환경/자료 점검·계획·기록을 진행한다.

## 범위와 실행

- [업무 유형별 기준](references/task-profiles.md)에서 해당 유형만 읽는다. 업무 용어는 현 업무의 근거로 확정한다.
- 수용 기준은 관찰 가능한 입력→동작→출력으로 쓴다. 기능 목록·양식 존재만으로 완료를 정의하지 않는다.
- 테스트 묶음을 실행하기 전 목적·입력/조건·기대 결과와 방법을 짧게 설명하고, 실행 후 기대/실제 결과·판정·한계·테스트 위치를 쉬운 한국어로 보여준다. 개수/종료 코드만으로 보고를 끝내지 않는다. verify-result가 있으면 그 스킬의 사용자용 테스트 설명 기준을 읽고 SERVICE/probe의 현재 결과와 devlog의 실행 이력에 연결한다.
- 사용자 확인을 받은 계획과 기존 스택으로 가장 작은 작동 경로를 먼저 연결한다. 필수조건, 브리핑·확인 대기, 검증, 인계에 시간을 배정하고 남은 시간에 맞춰 부가 기능을 줄인다.
- 새 업무 또는 추가 구현·수정 요청은 자료·환경을 짧게 확인한 뒤 예상 소요 범위와 근거·미확인 조건, 구현/검증·기록 배분, 예상 인계 지점과 기존 목표에 미치는 영향을 먼저 알린다. 첫 질의 단계는 조건부 추정으로 제시하고 답변 뒤 갱신한다. 단순 설명 질문마다 시간을 붙이지 않으며 추정 안내를 별도 시작 승인으로 바꾸지 않는다. 자세한 기준은 [시간표](references/time-budget.md)를 따른다.
- 현재 도구로 접근할 수 없는 자료·외부 기능이 필요할 때만 [MCP·플러그인 선택](references/tool-connections.md)을 읽는다. 외부 연결을 미리 일괄 설치하거나 개인 계정·제한된 전송 권한을 가정하지 않는다.
- 새 결과물에 앱 뼈대가 필요하면 키트의 fullstack/api/frontend/data/rag 프로필 중 요구에 맞게 선택한다. 기존 프로젝트에는 스킬만 적용하고 불필요한 앱 전체를 설치하지 않는다. 복사된 예시 기능은 실제 수용 기준으로 교체한다.
- 구현은 `build-service`, 데이터는 `analyze-data`, 검증은 `verify-result`가 실제로 필요할 때 읽는다. 설치되어 있지 않으면 해당 역할을 직접 수행한다.
- 서비스 결과물은 업무 README.md/readme.md를 보존하고 별도 SERVICE.md에 현재 컴포넌트 관계·아키텍처 다이어그램·API 명세·업무/운영 규칙·근거·검증·효과/한계를 유지한다. build-service가 있으면 그 작성 기준/양식을 사용한다. 추가 문서 제한이 있으면 허용된 위치를 확인해 안내한다. 업무 코드가 생기기 전에는 문서 양식을 완성된 서비스 설명으로 쓰지 않는다.
- 코드 초보자를 위해 유스케이스·사용 흐름·화면/API 라우팅·모듈 계약·대표 입력의 실제 호출 순서와 한국어 설명 주석을 함께 준비한다. 최적화 기준/포기한 점, 생성과 독립 검사, 백그라운드 중복/실패/재시작 정책, 조건 변화 입력/지표는 해당 기능일 때 실제 근거로 연결한다. 전체화면 유지 등 환경 제약을 브리핑과 UI 점검에 포함하고 감독 동작을 변경하지 않는다. 라이브러리/폴더 목록이나 문서 존재를 사용자 이해 완료로 취급하지 않는다.
- [시간 계획과 인계 기준](references/time-budget.md)의 기본 180분 집중 세션을 적용한다. T+60분에 필수 구현·대표 검증·읽을 자료를 1차 인계하고, T+60~120분에는 보완과 코드 이해를 병행한다. 지연 시 1차 인계 목표를 T+80분으로 조정하되 T+120분부터 마지막 60분은 코드 이해만 수행한다. 다른 기간/마감을 사용자가 지정하면 그 조건을 우선하고 이해 구간에 미치는 영향을 설명한다.
- 첫 작동 경로에 필수 기능과 대표 검증을 포함하고 합의한 중간 점검 시점에 남은 작업을 재추정한다. 확장 요구 때문에 인계를 늦추기 전 범위·일정 영향을 설명한다. 필수 요구의 누락을 감추지 않으며, 합의 일정이 어려우면 현재 상태·대안·남은 검토 시간을 알린다.
- README 파악 뒤 **업무 프로젝트 폴더**의 devlog.md와 probe.md를 확인한다. 자동 세션으로 준비하며 배포 키트 내부에는 만들지 않는다. `record-work`의 기준을 읽고 중요한 결정·변경·검증 및 턴 종료 전에 별도 사용자 요청 없이 갱신한다. `devlog.md`는 사건·질의응답·사용자 판단 이력, `probe.md`는 페르소나→페인포인트→원인·근거→해결 원리→기능/코드/기술 선택→검증·업무 효과의 현행 연결을 관리한다. 자동 파일 관측을 의미 있는 설명의 대체물로 쓰지 않는다.
- 1차 인계에는 실행 명령·실행 시간, 기능 목록, 현재 diff, 읽을 파일/함수 순서, 실패/미검증을 포함한다. T+120분 전 보완은 `explain-work`와 `verify-result`를 함께 사용하고 사용자가 읽는 코드의 변경 위치·이유·영향을 먼저 알린다. T+120분부터는 기능 추가·리팩터링·자동 오류 수정·장시간 문서 작성/검증을 멈추고 설명·입력 예측·코드 추적·기존 결과 대조만 지원한다. 발견한 오류는 수정 후보로 남긴다. 이 구간의 변경은 사용자 명시 요청이 있을 때만 시간 영향을 설명하고 요청 범위에서 수행한다.
- 첫 실행의 실제 시간을 기록해 필요한 보완·회귀 검사가 T+120분 전에 끝나도록 계획한다. 인계/변경 중단 시점을 넘길 작업은 미리 알리고 범위·실행 계획을 조정한다. 대표 입력만 확인한 경우 전체 검증으로 확대해 쓰지 않는다.
- 새 세션에서는 실제 파일·저장된 기록·계획 확인 범위·현재 실행 결과를 대조한 뒤 이어간다. 이전의 완료 주장만 믿지 않는다. 이미 같은 계획에 대한 사용자 확인이 있으면 반복하지 않고, 결과물·중요 규칙·구조·인계 시점이 크게 달라지면 변경 부분을 다시 브리핑하고 확인받는다.
- 업무 세션을 마치거나 사용자가 종료를 요청하면 자동 세션 stop으로 최종 스냅샷·종료를 확인한다. 후속 작업은 담당자와 합의한 범위·권한·일정에 따라 이어간다.

## 업무 환경과 권한

조직·프로젝트의 데이터 접근·외부 전송·도구/모델 사용·인증 정책을 확인한다. 필요한 연결은 허용된 자격 증명과 데이터 범위에서 사용하며 기밀 값은 문서나 클라이언트 코드에 복사하지 않는다. 원격 전송·배포·외부 메시지 등은 사용자 지시와 합의한 업무 흐름의 권한 범위에서 수행한다. 환경이 차단한 작업은 우회하지 않고 원인·영향·가능한 대안을 담당자에게 알린다.

별도 후속 문항이 안내된 경우에만 [후속 절차 참고](references/followup-guidance.md)를 읽는다. 6문항·문항별 5분·총 30분과 해당 도구 사용 제한을 유지하되 일반 업무 흐름에 자동 적용하지 않는다. 180분 집중 세션과의 포함 관계·실제 마감은 현재 안내로 확인한다.

첫 질의 단계의 반환: 문제·페르소나·원인 가설, 담당자 질문/이유/구현 영향, 조건부 예상 시간과 답변 대기. 답변 반영 단계의 반환: 확정 규칙·열린 질문, 상세 구현 브리핑, 갱신한 시간과 사용자 계획 확인 대기. 계획 확인 뒤의 반환: 합의 범위의 실제 구현·검증·인계 결과. 질의응답과 구현 전 계획 확인을 건너뛰지 않으며, 이미 확인한 같은 범위의 시작 승인을 반복하지 않는다.
