# 구현 전 상세 브리핑과 사용자 확인

담당자 답변을 반영한 뒤 사용자가 **어떤 결과물이 만들어지고, 무엇을 어떻게 구현하는지 예상할 수 있게** 설명한다. 에이전트 내부 계획이나 작업 목록만 남기는 것은 브리핑이 아니다. 채팅에 실제 내용을 제시하고 사용자 확인을 받은 뒤 업무 구현을 시작한다.

## 언제 시작하고 어디서 멈추는가

- 문제·담당자 답변·기존 코드·환경·인계 계약을 근거로 계획을 만든다. 이미 확인한 답변을 다시 묻지 않는다. 중요한 업무 정책이 미확인이면 그 부분을 별도 표시한다.
- 확인 전에는 읽기 전용 코드/표본/스키마·실행 환경 점검, 기존 상태 확인, 기록·계획 작성만 진행한다. 앱 뼈대 복사, 업무 코드 작성/수정, 결과 데이터 변환·모델 학습, 계획 검증을 명목으로 한 기능 프로토타입 구현을 시작하지 않는다.
- 자료 설명을 새 결과물의 확정 동작으로 바꾸지 않는다. 설계·화면·파일·기술은 **제안/계획**, 실제 존재하는 기존 기능은 **확인된 현재 상태**로 구분한다.

## 브리핑에 담을 내용

### 1. 이해한 문제와 답변 반영

누가 어떤 순간에 어떤 결정을 내려야 하는지, 현재 페인포인트와 원인 근거/가설, 이번에 바꾸려는 흐름을 설명한다. 담당자 답변→확정 규칙→기능/수용 기준을 연결하고 남은 미확인·충돌을 밝힌다.

### 2. 완성 결과물의 모습과 사용 시나리오

산출물 형식과 실행/전달 방법을 먼저 보여준다. 웹이면 첫 화면의 영역·입력·버튼·표/차트·결과·오류 상태를 글이나 간단한 와이어프레임으로 제시한다. 표/파일이면 열·행·단위·정렬과 출력 형식, AI/분석이면 질문·입력→근거/계산→결과·해석을 보여준다. 사용자 행동 1개를 처음부터 끝까지 따라가며 어떤 결과가 나타날지 설명한다. 예시는 합성 예시이며 실제 실행 결과가 아님을 표시한다.

### 3. 기능별 구현 계약과 범위

| 기능 ID·우선순위 | 연결 요구·사용자 문제 | 사용자 행동·입력 | 처리 규칙·예외 | 출력·보이는 변화 | 확인할 수용 사례 |
| --- | --- | --- | --- | --- | --- |

필수·선택·이번에 제외할 범위를 나누고 제외 이유와 사용자 영향을 설명한다. 기능 이름만 나열하지 않는다. 저장·새로고침/재실행·빈 결과·잘못된 입력·실패 시 동작을 실제 요구에 맞게 설명한다.

### 4. 데이터 흐름과 기술 구조

입력→경계 검증→핵심 업무 로직→저장/모델/검색→출력의 흐름, 컴포넌트·모듈별 책임과 연결 계약을 설명한다. 의미가 있으면 간단한 다이어그램을 사용한다. 수정할 기존 파일과 만들 계획인 파일/함수를 구분하고, 기존 코드를 어떻게 보존할지도 적는다.

웹은 화면/API/저장 책임, 주요 메서드·경로·요청/응답·인증/공개 범위, 상태/문서 경로를 포함한다. 분석·ML은 행/단위·분모·전처리·분할·기준선·지표·누수 방지, RAG는 자료 처리·검색/생성 구분·근거 부족·인용 검증, 최적화는 목적·제약·실행 제한을 해당되는 만큼 설명한다. 업무와 무관한 계층·외부 연결을 추가하지 않는다.

### 5. 기술 선택·대안·선택 이유

| 중요한 결정 | 추천 방법·역할 | 같은 목적의 현실적 대안 | 각 장점·단점 | 이번 제약에서 추천하는 이유·감수할 한계 |
| --- | --- | --- | --- | --- |

라이브러리 이름 대신 무엇을 담당하는지 풀어 설명한다. 중요한 선택에 보통 1~2개 대안을 비교하고 설치·설정·운영·정확성·설명 가능성·시간 중 판단을 바꾸는 축을 사용한다. 대안 두 개를 실제 구현하는 것을 기본 절차로 삼지 않는다. 미측정 성능은 추정/미측정, 지정 기술은 업무 지정으로 밝힌다. 담당자 정책을 기술 취향으로 바꾸지 않는다.

### 6. 구현 전 검토와 검증 계획

자기 설계를 깨뜨릴 수 있는 중요한 사례를 먼저 검토한다. 모호한 규칙, 분모/경계, 상태 불일치, 데이터 손실, 권한/공개 범위 등 해당 업무의 실제 위험을 고르고 대응·남은 질문을 설명한다. 확인된 문제와 아직 검증하지 않은 위험을 구분한다.

대표 정상·경계·실패 입력, 독립된 기대값의 근거, 자동/HTTP 검사와 사용자 수동 확인, 예상 결과를 제시한다. 아직 실행하지 않은 검사는 계획이다. 구현 뒤에는 승인한 기능과 실제 결과를 대조하고 재현 가능한 오류·회귀를 검증한다.

### 7. 구현 순서와 시간·인계

설계 확인→핵심 경로→기능별 검증→기록 정합→코드 인계의 순서와 예상 시간 범위를 제시한다. 브리핑·수정·사용자 확인 대기도 전체 경과시간에 포함하며 별도로 미정인 대기 시간을 숨기지 않는다. 이번 업무의 마감과 담당자 리뷰·사용자 코드 이해·직접 검증 시간을 기준으로 인계 시점을 제안한다. 시간이 부족하면 범위·일정 대안을 설명하고 사용자 계획 확인은 유지한다.

기본 180분 집중 세션의 기능별 1차 구현 범위(T+60분), 보완/수정+이해 구간(T+60~120분), 코드 변경 없는 이해 구간(T+120~180분)을 브리핑에 명시한다. 지연 시 T+80분 인계로 조정해도 T+120분 변경 중단은 유지한다. 비용이 큰 선택과 새 기능 요청이 어느 구간을 사용하는지 알리고 마지막 60분은 개발 여유로 계산하지 않는다.

## 사용자가 계획을 확인한 뒤 구현

브리핑에서 실제 업무에 해당하는 아래 항목도 다룬다. 라이브러리를 나열하는 설명으로 대신하지 않는다.

- 사용자 목표별 유스케이스, 정상/오류 흐름, 화면 라우팅과 API 진입점, 각 모듈의 입력·출력·연결 순서. 사용자가 보게 될 결과와 함께 설명한다.
- 결과를 선택하는 알고리즘이 있으면 반드시 지킬 조건과 더 좋은 결과의 기준, 실제 식/우선순위·단위·근거, 대안 대비 얻는 점/포기하는 점, 조건을 만족할 결과가 없을 때의 처리.
- 비동기/백그라운드 작업이 필요하면 실행 위치, 중복 요청, 계산 중 읽기/수정, 실패·시간 초과·재시작, 결과 게시 정책과 남는 한계. ‘async 사용’만으로 설명을 끝내지 않는다.
- 전체화면 유지 등 실행 환경의 UI 제약과 금지된 전환/대화상자, 허용 환경에서 확인할 방법. 이 조건과 필수 기능이 충돌하면 먼저 사용자에게 알린다.
- 코드 초보자를 위한 상세 한국어 주석, SERVICE.md의 읽는 지도, 독립적인 규칙 검사와 조건 변화 확인을 어느 시점에 준비할지. 기본 세션의 T+120분까지 준비를 마친다.

build-service가 사용 가능하면 해당 스킬의 `references/code-understanding.md`, `decision-criteria.md`, `background-work.md`, `fullscreen-compatibility.md` 중 관련 기준을 읽는다. 선택 설치로 없어도 위 브리핑 내용은 유지한다.

브리핑 끝에는 **이 계획대로 진행 / 특정 기능·화면·기술을 수정 / 더 설명이 필요한 부분**을 사용자가 정할 수 있게 요청하고 응답을 기다린다. 사용자 선택이 필요한 한 가지가 있다면 추천·장단점·영향을 먼저 제시한다. 상세 브리핑을 보여준 턴에서 곧바로 업무 코드를 작성하지 않는다.

- 제시한 계획에 대한 명확한 진행 의사만 확인으로 기록한다. 담당자 답변 전달, 최초의 일반적인 업무 시작 요청, 침묵·시간 경과를 설계 확인으로 취급하지 않는다.
- 계획 수정 요청을 받으면 해당 기능·구조·대안·시간 영향을 반영한 수정본을 설명한다. 수정 요청만으로 그 계획의 구현까지 승인한 것으로 해석하지 않는다.
- 이미 같은 계획과 범위에 대한 사용자 확인이 있으면 반복 요청하지 않는다. 합의한 범위의 통상 구현·검증·오류 수정은 계속한다. 사용자에게 보이는 결과·중요한 업무 규칙·저장/API 계약·기술 구조·인계 시점이 크게 달라지면 바뀌는 부분을 다시 브리핑하고 확인받는다.
- 사용자가 이 확인 절차를 생략하고 진행하라고 명시적으로 지시한 경우만 그 범위와 근거를 기록한다. 에이전트가 시간 부족을 이유로 생략하지 않는다.

## 기록과 설명

probe.md에 브리핑 ID/버전, 제안한 결과물·기능·구조·대안·검증·시간, 확인 대기/확인됨·사용자 실제 답변·적용 범위를 유지한다. 별도 세 번째 계획 파일을 기본 생성하지 않는다. devlog.md에는 브리핑·수정·사용자 확인 사건을 실제 시점에 남긴다. 계획이 있다는 사실은 구현·검증 완료가 아니다.

인계 때 합의 계획→현재 구현→실제 확인 결과를 대조해 달라진 점·미완성을 설명한다. 사용자가 예상한 결과물과 실제 결과물의 차이를 숨기지 않는다. 기능 하나의 사용 장면→데이터/코드 흐름→기술 선택 이유→작은 입력의 직접 확인 순서로 설명을 이어간다.
