# 짧은 시작과 자동 세션

`$solve-task`만 입력하거나 “업무 시작해줘”라고 요청하면 기본 시작 흐름을 수행한다. 긴 시작 프롬프트를 다시 요구하지 않는다. 기존 업무·사용자 지침과 현재 AI 허용 단계가 우선한다.

## 시작

1. 실제 업무 루트, README·AGENTS, 산출물과 추가 문서 제한을 읽는다. 배포 키트 자체에는 적용하지 않는다.
2. 이 스킬의 `scripts/session.py start --root <실제 업무 루트>`를 실행한다. 설치 모드는 record-work와 git-checkpoint도 포함한다. 설치가 제한된 reference 모드면 공개 클론의 entry_path와 session_script, 스킬별 경로를 사용한다. 대상의 `.agents`를 다시 만들려고 하지 않는다.
3. 응답의 `status=running`과 `last_snapshot.status=saved|unchanged`, 스냅샷 위치를 확인한다. 시작 오류·중단·파일 제외를 숨기지 않는다. 환경에서 백그라운드 실행이 차단되면 우회하지 않고 사용자에게 미작동 상태를 알리고 플랫폼 문의로 연결한다.
4. record-work의 작성 기준을 읽고 devlog.md의 현재 단계와 probe.md의 문제·페르소나·페인포인트·원인 가설·질문을 실제 업무 내용으로 채운다. 형식만 생성한 상태로 분석 완료라고 하지 않는다.
5. 문제 입력→담당자 질문 제안→확인한 답변 반영→[상세 구현 브리핑](implementation-brief.md)→사용자 계획 확인→필요한 뼈대 적용·구현→대표 검증→코드 이해 인계로 이어간다. 질문 답변 대기와 설계 확인 대기는 별개이며 브리핑을 보여준 턴에 구현하지 않는다. 이미 확인한 같은 범위는 반복 확인하지 않는다. 질의·브리핑·확인 대기도 경과시간에 포함하고 업무 범위·예상 소요·마감·검토 시간을 근거로 인계를 계획한다. 실제 업무 시작 시각과 감시 세션 시작 시각을 구분한다.

기본 집중 세션은 180분이다. T+60분 1차 인계(지연 시 T+80분), T+120분까지 보완과 이해 병행, T+120~180분 변경 없는 이해를 적용한다. 감시 세션을 늦게 시작하거나 재시작해도 업무 시간 경계를 다시 계산하지 않는다. 마지막 구간에는 기존 저장 보호만 유지하고 에이전트는 코드 변경·문서 확장을 진행하지 않는다. 후속 문항이 명시되면 [후속 절차 참고](followup-guidance.md)를 확인하고 금지된 단계로 자동 감시를 넘기지 않는다.

별도 사용자 설정 없이 180초마다, 최대 10800초 동안 로컬 스냅샷을 남긴다. 소스·설정·문서 경로는 매번 다시 발견하므로 새 폴더도 포함한다. 중복 호출은 실행 중인 세션을 재사용한다. Git 유무와 관계없이 **업무 폴더의 `.local/ai-toolkit/snapshots/`**에 저장하고 관리되는 `.git`은 수정하지 않는다. Git 초기화·자동 stage/commit/push도 하지 않는다. 업무 폴더 바로 아래에 키트 클론이 있어도 배포 마커가 있는 디렉터리는 자동 사본에서 제외한다.

필요한 감시 기간이 더 짧으면 `--duration <초, 최대 10800>`으로 지정한다. 이 상한은 백그라운드 프로세스의 안전 제한이며 업무 마감이 아니다. 업무가 계속되면 상태와 필요를 확인해 다시 시작할 수 있고, 현재 마감이나 경과시간을 알 수 없으면 임의로 만들지 않는다.

기본 자동 선택은 CSV, 비밀 파일명, 숨김 도구 폴더, 생성물·의존성·바이너리·크기 초과 파일을 제외한다. CSV와 대용량 데이터는 별도 저장 계약을 따른다. 이름 필터는 모든 비밀정보를 찾아내는 도구가 아니다. 제외 항목은 status에서 확인하고 필요하면 선택형 checkpoint 도구를 사용한다.

reference 모드에서 앱 뼈대가 필요하면 키트의 install.py에 `--templates-only`와 필요한 profile/modules를 지정한다. .agents 설치를 재시도하지 않으며 기존 업무 파일은 보존한다. 일반 작업 폴더 자체의 쓰기나 감시 실행이 금지된 경우에는 해당 상태를 알리고 임의로 권한·플랫폼 설정을 바꾸지 않는다.

## 기록 갱신: 별도 호출을 요구하지 않는다

- 문제/질의 단계: devlog에 현재 단계·확인 사실·가정·담당자 질문·사용자 판단 대기, probe에 페르소나·페인포인트·영향·원인 가설과 근거.
- 답변·범위 확정 뒤: devlog에 실제 답변·결정·변경 이유, probe에 문제→해결 원리→요구/기능과 수용 기준.
- 구현 전 브리핑·사용자 확인: probe에 제안 결과물·기능/구조/대안·검증/시간·계획 버전·확인 상태/범위, devlog에 실제 설명·수정·사용자 답변과 인계 영향. 계획과 실제 구현을 구분한다.
- 기술 선택·구현 변경 뒤: devlog에 목적·변경·실패/수정, probe에 코드 위치·선택 도구·현실적 대안·각 장단점·선택 결론·한계.
- 서비스 구현/변경 뒤: 업무 README는 보존하고 SERVICE.md의 현재 컴포넌트/다이어그램·API·규칙/근거·실행·검증/효과를 갱신한다. probe에는 핵심 요약과 상세 위치, devlog에는 실제 사건을 연결한다. 양식 생성만으로 서비스 문서가 완성됐다고 하지 않는다.
- 검증 뒤: devlog에 실제 명령·결과·근거, probe의 해당 기능에 기대값/실제값·통과/실패·미검증 범위.
- 사용자에게 코드 인계하거나 작업 턴을 마치기 전: 기능 목록↔코드↔검증↔문서의 누락을 대조하고 변경한 기능만 갱신한다. 사용자 이해는 확인 전까지 대기다.
- 긴 실행 중에는 의미 있는 경계에서 갱신한다. 매 도구 호출마다 문서를 쓰거나 같은 내용을 반복해 구현 시간을 소모하지 않는다.

파일 감시 도구는 devlog에 관측된 파일명·해시 변화만 자동 추가한다. 변경 의도·테스트 성공·기술 선택 이유를 추정하지 않는다. 이 의미 있는 설명과 probe의 현행 갱신은 **현재 작업을 수행하는 Codex의 책임**이다. 감시 도구는 모델을 호출하지 않으며 추가 토큰을 소비하지 않는다.

## 유지·종료

인계와 세션 재개 시 `scripts/session.py status --root <업무 루트>`로 실제 실행을 확인한다. `interrupted`이면 마지막 사본과 현재 파일을 비교한 뒤 필요한 경우 start로 재시작한다. 설치만으로 실행되었다고 주장하지 않는다.

업무 세션을 마치거나 사용자가 종료를 요청하면 `scripts/session.py stop --root <업무 루트>`로 최종 스냅샷과 종료를 확인한다. 후속 작업은 합의한 범위·권한·일정에 따라 이어간다. 사용자가 “자동저장 끄기”라고 요청해도 같은 stop을 사용한다. 관련 없는 프로세스는 종료하지 않는다.

추가 기록 파일이 금지되면 `start --no-records`로 실행하고 허용 문서에 해당 내용을 유지한다. 자동저장 금지·추가 파일 금지 등 명시된 운영 제약이나 사용자의 해제 요청이 있으면 해당 자동 동작을 수행하지 않는다. 에디터 미저장 버퍼와 프로세스는 스냅샷으로 복구되지 않는다.
