# 업무 범위·견적·검토 시간을 반영한 일정 계획

업무의 목표·범위·의존성·마감·담당자 응답 가능 시간에 맞춰 일정을 제안한다. 사용자가 지정한 기본 집중 세션은 아래의 180분 운영안이다. 업무 전체의 총기간을 180분으로 단정하지 않으며, 사용자가 다른 기간/마감을 명시하면 그 조건과 이해 시간에 미치는 영향을 반영한다.

## 기본 180분: 1차 구현 60 + 보완/이해 60 + 온전한 이해 60

| 경과 | 목표 | 완료/중단 기준 |
| --- | --- | --- |
| T+0~60분 | 문제 분석·담당자 질문/답변·상세 브리핑/계획 확인·필수 구현·대표 검증 | T+60분에 1차 코드를 인계하고 기능/실행 방법·읽을 코드 순서·문서·미완성/미검증을 안내 |
| T+60~120분 | 디벨롭·수정/보완과 코드 이해 병행 | 합의한 보완을 구현/검증하고 사용자에게 변경 위치·이유·영향을 먼저 설명. T+120분까지 현재 코드와 설명 자료 정합 마무리 |
| T+120~180분 | 온전히 코드 이해 | 코드/설정/테스트 변경·새 기능·리팩터링·자동 오류 수정 중단. 구조·입출력 흐름·업무 규칙·기술 선택·기존 검증 근거를 읽고 설명 |

질의·브리핑·사용자 계획 확인도 첫 구간의 경과시간에 포함한다. 사용자 확인을 생략하거나 답변 수신 시 시계를 다시 시작하지 않는다. T+60분 인계는 코드 파일 존재가 아니라 필수 동작과 대표 확인, 이해를 시작할 자료를 갖춘 상태를 목표로 한다. 준비되지 않은 부분은 그대로 표시한다.

단계 전환과 의미 있는 작업 시작 전에 확인한 업무 시작/현재 시각을 근거로 경과시간과 현재 구간을 확인한다. 시작 시각을 모르면 경과를 지어내지 않는다. T+120분을 넘길 것으로 예상되는 새 구현·장시간 검증은 시작하지 않고 범위·현재 상태·남은 항목을 설명한다.

### 지연 시 T+80분 인계 대안

T+35~40분에 범위·실행 소요와 남은 작업을 점검한다. T+60분 인계가 어려우면 원인·현재 상태·줄일 범위·검증 영향을 설명하고 T+80분을 대안 목표로 알린다. 이 경우 보완/이해 병행 구간은 T+80~120분의 40분이다. **T+120분 코드 변경 중단과 T+120~180분 이해 60분은 유지한다.**

미완성이나 새 요청 때문에 마지막 구간을 자동으로 개발 시간으로 바꾸지 않는다. 사용자가 이 구간의 수정을 명시적으로 요청하면 이해 시간에 주는 영향을 먼저 알리고 요청 범위만 수행한다. 그 외 오류·개선점은 수정 후보와 근거로 남긴다.

### 마지막 60분에 할 일

사용자가 대표 입력의 결과를 먼저 예상하고, 컴포넌트 관계/다이어그램→진입점/함수→업무 규칙/예외→API/출력→선택 이유/대안→기존 확인 결과를 추적한다. 필요하면 준비된 작은 사례를 함께 확인하되 새 기능 구현·튜닝·장시간 재검증으로 확장하지 않는다.

SERVICE.md·probe.md·devlog.md의 주요 설명은 T+120분 전에 현재 코드와 맞춘다. 마지막 구간에는 이해에 직접 필요한 짧은 확인 메모만 남기고 문서 확장/미작성 구획 보완을 진행하지 않는다. 이해 확인은 실제 사용자 설명과 직접 확인 범위만 기록한다.

### 인계·후속 절차

필수 산출물·실행 안내·저장/검증 상태 확인을 T+120분 이전에 준비한다. 실제 제출/인계 확정 절차에 별도 시각이 요구되면 현재 안내로 확인하고 영향을 사용자에게 알린다. 마지막 이해 60분에서 임의로 별도 버퍼를 떼지 않는다.

후속 문항이 안내된 경우에만 [후속 절차 참고](followup-guidance.md)를 사용한다. 6문항×5분=30분의 구성·도구 제한을 보존하고, 180분과 별도인지 같은 전체 마감에 포함되는지 확인한다. 현재 업무 흐름을 후속 문항 중심으로 바꾸지 않는다.

## 요청을 받았을 때 예상 시간 안내

- 새 업무 또는 추가 구현·수정 요청의 관련 파일·실행 환경·현재 상태를 짧게 확인하고 작업 전에 예상 소요 범위를 알린다. 단순 설명·확인 질문마다 시간을 붙이지 않는다.
- 요구 확인, 상세 브리핑·계획 수정, 설치/설정, 구현, 검증·기록, 담당자 인계·사용자 리뷰 시간을 구분한다. 담당자 답변/계획 확인 대기가 미정이면 별도로 표시하고 실제 경과시간에는 포함한다.
- 지금부터 남은 예상 소요, 실제로 확인한 업무 경과시간, 예상 인계 시점을 구분한다. 시작 시각을 확인할 수 없으면 임의 T+나 완료 시각을 만들지 않는다.
- 예상 시간의 근거와 불확실성, 외부 의존성·권한·데이터·실행 비용을 밝힌다. 정밀한 단일 숫자를 보장하는 대신 범위와 재확인 시점을 제시한다.
- 추가 요청이 기존 기능·품질·인계 일정·리뷰 시간에 주는 영향을 설명한다. 중요한 범위 선택은 대안·추천과 함께 사용자에게 확인하고 기존에 합의한 같은 범위의 승인은 반복하지 않는다.

안내 형식: **예상 X~Y분/시간(브리핑·구현·검증/기록 배분). 전제·미확인 조건. 담당자 확인 대기. 제안 인계/리뷰 시점과 현재 마감에 미치는 영향.** 단위와 값은 실제 업무 규모에 맞춰 쓴다.

## 단계별 계획과 완료 기준

| 단계 | 할 일 | 다음 단계로 갈 근거 |
| --- | --- | --- |
| 요구·환경 파악 | 사용자/업무 흐름·목표·자료·기존 코드·운영 제약·산출물 확인 | 확인한 사실·수용 기준·열린 질문 |
| 담당자 협의 | 결과를 바꾸는 질문과 답변·충돌·우선순위 반영 | 업무 규칙과 범위의 근거 |
| 상세 브리핑·계획 확인 | 결과물·사용 흐름·설계/대안·위험/검증·일정 설명 | 제시한 계획에 대한 사용자 확인 |
| 핵심 경로 구현 | 합의한 범위의 작은 작동 경로부터 연결 | 실제 입력→업무 처리→출력과 대표 검증 |
| 검토·수정 | 코드/문서·정상/경계/실패·운영 조건 확인 | 확인된 오류와 미검증 위험·필수 수정 결과 |
| 설명·업무 인계 | 구조·선택 이유·실행/운영·근거·남은 항목 공유 | 담당자가 사용할 수 있는 산출물과 확인 범위 |
| 후속 작업 | 운영 결과·새 요구·미해결 사항 반영 | 새 범위/일정·필요한 계획 변경 확인 |

이 표는 단계별 완료 기준이다. 시간 경계는 위의 기본 180분 집중 세션 또는 현재 사용자가 명시한 다른 일정에 따른다. 짧은 업무에도 필요한 브리핑을 생략하지 않되 규모에 맞는 깊이로 설명한다.

## 진행 중 재추정

담당자 답변 수신, 범위/의존성 변경, 첫 실제 실행, 오류나 운영 조건 변화 시 남은 작업과 예상 시간을 갱신한다. 지연 원인·현재 완료 범위·남은 검증·마감 영향·가능한 범위 조정을 짧게 알리고 중요한 변화는 devlog.md에 남긴다.

답변 대기가 길어지면 독립적인 읽기 전용 점검과 기록을 진행한다. 답변이나 계획 확인을 추정하지 않으며 사용자 확인 전 업무 구현을 시작하지 않는다. 인계 목표를 맞추려고 미완성·미검증을 완료로 표시하지 않는다.

## 실행과 리뷰 시간 확보

실제 실행 시간을 측정해 재실행·회귀 검사·인계 전에 필요한 여유를 계획한다. 전체 실행을 마감 전에 끝낼 수 없으면 확인한 대표 범위와 NOT_RUN 범위, 사용자 영향을 구분한다. 측정하지 않은 실행 시간을 단정하지 않는다.

사용자가 코드를 읽거나 담당자가 검토하는 동안은 설명·기존 근거 대조를 지원한다. 보완과 오류 수정은 기본 세션의 T+120분 전에 진행하며 중요한 변경은 위치·이유·영향을 먼저 알린다. 마지막 60분에는 현재 코드를 유지하고 이해에 집중한다.

## 세션과 업무 마감의 구분

자동저장 도구의 최대 10800초는 백그라운드 감시의 안전 상한이며 업무 완료 시한이 아니다. 필요한 저장 기간을 명시하고 만료 뒤에는 상태와 필요를 확인해 다시 시작할 수 있다. 업무 세션 종료나 사용자 요청 시 최종 사본과 감시 종료를 확인한다. 인계 후 변경은 합의한 후속 범위와 버전/검증 기록으로 관리한다.
