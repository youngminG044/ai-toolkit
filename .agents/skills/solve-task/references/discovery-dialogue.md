# 문제 입력 → 담당자 질문 → 답변 반영 → 상세 브리핑 → 사용자 확인 → 구현

사용자가 문제 상황과 업무 목표를 주면 먼저 문제를 정의하고 **사용자가 업무 담당자에게 직접 보낼 질문**을 준비한다. 첫 응답에서 업무 기능 코드를 작성하거나 앱 뼈대를 설치하지 않는다. 기존 대화에서 질문·답변 반영이 이미 끝났으면 같은 대기를 반복하지 않는다. 다음은 사용자에게 구현 계획을 상세히 설명하고 확인받는 단계다.

## 첫 응답: 문제와 질문을 정리하고 답변을 기다린다

1. README·기존 지침·제공 파일과 사용자 설명을 읽고 문제 상황, 업무 목표, 필수 산출물·제약을 짧게 정리한다. 사용자가 이미 입력한 내용을 다시 요구하지 않는다. 상황이 비어 있으면 사용자가 받은 문제 설명을 입력하도록 요청하고 확인 가능한 자료부터 읽는다.
2. 누가 어떤 업무 목표를 갖고 어떤 상황에서 어려움을 겪는지 정리한다. 페르소나는 근거 있는 역할·목표·업무 환경으로 표현한다. 가상의 이름·나이·성향을 만들지 않는다.
3. 현상과 페인포인트, 영향, 원인 가설을 분리한다. 자료에 있는 설명, 담당자 진술, 코드/데이터로 관측한 사실, 가정·미확인을 구분한다. 담당자가 원인이라고 말했다는 이유만으로 인과가 입증됐다고 하지 않는다.
4. 구현·검증을 바꾸는 질문부터 보통 3~5개 제안한다. 필요한 질문이 더 적으면 그만큼만 제시한다. 이미 자료에서 확인한 답은 출처와 함께 요약하고 재질문하지 않는다.
5. 질문마다 **그대로 보낼 문장 / 확인하는 이유 / 답변에 따라 달라질 기능·규칙·수용 기준 / 우선순위**를 붙인다. 여러 상대가 있으면 적절한 담당자도 표시한다. 추천 기술에 동의하도록 유도하는 질문을 만들지 않는다.
6. 사용자가 담당자에게 질문한 뒤 답변을 같은 Codex 대화에 붙여넣도록 안내하고 이 단계의 응답을 마친다. 사용자를 대신해 메시지를 보내거나 담당자의 답을 추정하지 않는다. 사용자가 별도로 메시지 전송을 지시한 경우는 그 허용 범위에 따른다.

질문 주제는 현재 누락에 맞춰 선택한다. 예를 들어 실제 사용자와 결정, 현재 업무 단계·빈도·손실, 원인의 근거, 정상/예외 규칙, 오판 비용, 데이터·권한·사용 환경, 완료 기준과 측정 위치가 있다. 모든 주제를 양식처럼 질문하지 않는다.

대기 중에는 환경·기존 실행 명령·데이터 구조 확인과 기록 준비를 할 수 있다. 답변에 의존하는 업무 로직·기술 선택·뼈대 설치를 확정하지 않는다. devlog에는 현재 단계 `담당자 답변 대기`, 열린 질문과 다음 행동을 남긴다. probe에는 확인된 문제·페르소나·가설·질문을 작성한다.

## 답변을 받으면: 반영하고 구현 전 브리핑으로 이어간다

- 질문 ID와 답변·출처를 연결하고 확인된 사실, 여전히 열린 항목, 기존 자료와의 충돌을 갱신한다. 사용자가 제공하지 않은 답을 채우지 않는다.
- 페르소나 → 페인포인트·영향 → 원인·근거 → 해결 원리 → 기능·업무 규칙 → 수용 기준을 연결한다. 구현과 무관한 인물 묘사나 기능 목록으로 끝내지 않는다.
- 미확인 업무 정책이나 충돌이 결과를 바꾸면 해당 부분만 다시 질문한다. 영향이 없는 작업은 계속한다. 질문에 답을 못 받았을 때는 임시 가정의 영향과 대안을 제시하고, 중요한 가정을 적용하기 전 사용자의 판단을 받는다.
- 필요한 답과 판단이 확보되면 [구현 전 상세 브리핑](implementation-brief.md)을 읽는다. 최종 결과물의 모습·사용 시나리오, 기능별 입력/처리/출력·예외, 데이터 흐름·기술 구조·변경 파일, 추천 방법/대안과 장단점, 검증·시간을 실제 사용자에게 설명한다. 내부 계획이나 짧은 작업 목록으로 대신하지 않는다.
- 브리핑을 보여준 응답은 사용자 계획 확인 대기로 마친다. 담당자 답변을 받았다는 이유로 업무 코드·뼈대를 작성하거나, 같은 턴에서 브리핑 후 바로 구현하지 않는다. 계획을 수정하면 바뀐 내용과 시간 영향을 설명하고 확인을 기다린다.
- 사용자가 제시한 계획을 확인한 뒤 합의한 범위의 구현·검증으로 이어간다. 같은 계획에 대한 확인은 반복하지 않으며 중대한 결과물/구조 변경은 먼저 다시 브리핑한다.
- 답변 대기도 실제 경과시간에 포함한다. 확인한 시작 시각·담당자 응답·업무 마감을 기준으로 남은 작업과 예상 소요를 갱신한다. 현재 업무의 인계·리뷰 일정에 미치는 영향을 설명하고 필요한 범위 조정을 합의한다.
- 기본 180분 세션에서는 질의·브리핑·계획 확인을 포함해 T+60분 1차 인계를 목표로 한다. 지연 시 T+80분 대안을 알리되 T+120~180분은 코드 이해 전용으로 유지한다. 시간 압박을 이유로 사용자 계획 확인을 생략하지 않는다.

## 중간에 사용자 판단이 필요할 때

대상 사용자 우선순위, 업무 기준/임계값, 오류 간 비용, 필수 범위 변경, 중요한 품질·시간 절충처럼 **사용자의 의도나 업무 정책이 결정해야 하는 것**을 묻는다. 기존 답이 있는 내용이나 파일명·함수 분리 등 통상적인 구현 선택을 매번 승인받지 않는다.

질문은 다음을 포함한다.

- 지금 결정해야 하는 한 가지와 그 이유.
- 추천안과 현실적인 다른 선택지의 장단점.
- 각 선택이 기능·정확성·시간·검증에 미치는 영향.
- 답을 기다리는 동안 계속할 작업과 보류할 작업.

여러 쟁점은 독립적인 소수의 질문으로 묶는다. 중요한 결정은 답변 전 적용하지 않으며, 대기 시간이 흘렀다는 사실을 선택으로 간주하지 않는다. devlog에는 결정 이력, probe에는 현재 선택과 근거·영향을 유지한다.

## 기록과 인계

분석 단계부터 probe에 문제 정의와 사용자 맥락을 작성한다. 원인이 미확인이면 가설로 남기고, 해결책이 기능 수준에서 그 원인에 어떻게 작용하는지 설명한다. 근거가 부족하면 원인 해결이 아니라 증상 완화인 점과 남은 한계를 밝힌다.

코드·단위 테스트가 작동했다는 기술 검증과, 실제 업무 시간·오류·비용 등이 개선됐다는 업무 효과 검증을 구분한다. 측정하지 않은 개선율·절감 시간·원인 제거를 만들지 않는다. `record-work`의 문제/기능별 작성 기준을 사용한다.
