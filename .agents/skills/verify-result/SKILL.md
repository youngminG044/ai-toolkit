# 검증과 인계

검증을 시작하거나 결과를 인계할 때 [사용자용 테스트 설명](references/test-explanation.md)을 읽는다. 실행 전 무엇을 왜·어떤 입력/기대값으로 확인하는지 짧게 알리고, 실행 후 목적·입력/조건·기대 결과/근거·실제 결과·판정·한계를 쉬운 한국어로 설명한다. 실제 케이스/비교 코드와 출력을 대조하며 통과 개수나 기술 로그만으로 보고를 마치지 않는다.

기본 180분 집중 세션에서는 대표 검증을 포함해 T+60분 1차 인계, 필요 시 T+80분 대안을 목표로 한다. 보완·회귀·최종 정합 검사는 T+120분 전에 마친다. T+120~180분은 코드 이해 전용이므로 새 수정이나 장시간 검증을 시작하지 않고 기존 사례·기대값·결과를 함께 읽는다. 이때 발견한 오류는 자동으로 고치지 않으며 사용자 명시 요청이 있으면 시간 영향을 설명하고 요청 범위만 수행한다.

## 무엇을 검증할지

- 각 필수 요구에 실제 확인 방법을 붙인다. 파일 존재·빌드 성공·HTTP 200만으로 업무 동작이 맞다고 판단하지 않는다.
- 대표 정상 입력, 중요한 경계/실패, 고친 버그의 재현 사례를 고른다. 구현을 그대로 반복하는 테스트를 늘리지 않는다.
- 알고리즘은 가능한 작은 입력에서 단순한 기준 해법과 비교하고, 분석은 독립 계산·분할·분모를 확인한다.
- 생성 결과의 규칙 검사는 원본 입력·설정과 최종 출력을 대조한다. 생성 함수의 중간 판단을 그대로 정답으로 재사용하지 않는다. 누락·중복·수량/용량·필터·시간 등 해당 업무의 불변 조건과 수동 기대값을 확인하고, 검사기가 실제로 잘못된 결과를 잡는 반례도 고른다. 공용 단위 변환 등을 재사용한 범위와 검사하지 못한 외부 가정도 밝힌다.
- 최적화/판정 기능은 유효성 검사와 품질 비교를 분리한다. 주요 설정/분포를 바꾼 작은 사례에서 위반·미처리·평균/최대 지표·실행 시간을 비교한다. 이론상 예상과 실제 실행 비교를 구분하고 전역 최적을 검증 없이 주장하지 않는다.
- 백그라운드 작업이 있으면 동시/중복 요청, 계산 실패, 입력 변경·늦게 끝난 결과, 재시작의 현재 약속을 실제 코드와 대조한다. 필요한 사례만 허용된 격리 환경에서 실행하고 공유 플랫폼을 중단하지 않는다. 버튼 비활성화·202 응답은 서버 신뢰성 검증의 대체물이 아니다.
- 전체화면 유지가 요구되면 UI 변경 후 관련 소스/이벤트 경로에서 새 탭·페이지 이동·네이티브 창·다운로드·전체화면 API 등 위험 동작을 확인한다. 실제 환경 확인은 허용된 준비 공간에서만 진행하고 일부러 해제를 재현하지 않는다. 정적 검색·빌드는 실제 IDE 검증과 구분하며 감독 코드/로그를 바꾸지 않는다.
- 기존 프로젝트 검증 명령을 우선한다. `scripts/run_checks.py`에 명령을 argv 배열로 전달하면 shell 없이 실행하고 종료 코드·시간·출력을 JSON으로 남길 수 있다. 이 도구는 명령 결과 기록기이며 테스트 개수·커버리지·업무 규칙 충족을 자동 판정하지 않는다.
- 서버/API가 있는 결과물은 상태 경로·API 목록/스키마·대표 업무 경로를 실제 HTTP로 확인하고 실행 안내의 포트·경로와 대조한다. 문서 비공개 설정이 있으면 문서가 닫혀도 업무 API가 의도대로 동작하는지 확인한다. 상태 200과 업무 정확성은 구분한다.
- 서비스는 SERVICE.md의 컴포넌트/다이어그램 노드·연결, API 메서드/필드/오류, 업무/운영 규칙과 근거·실행 정보·검증/효과 주장을 실제 코드·입력·결과와 대조한다. 계획/미구현·미검증·미측정을 구분하고, 업무 README를 보존했는지 확인한다. Markdown API 명세 작성은 문서 URL의 공개 권한을 바꾸지 않는다.

## 합의 계획과 변경을 비판적으로 검토

- 사용자에게 브리핑한 기능·계약·선택 이유와 현재 코드/diff를 대조한다. 합의와 다른 동작, 누락, 불필요한 확장과 인계 영향을 확인하고 사용자에게 알린다.
- 중요한 실패 가설을 소수 고른다. 실제 입력→기대 결과의 근거→재현 명령/수동 절차→관측 결과→관련 위치를 연결하고, 실행 가능한 가설은 직접 확인한다. 같은 검사의 반복이나 모든 문제를 가정한 전면 재검토는 하지 않는다.
- 재현됐고 합의 요구를 위반한 것은 확인된 오류로, 아직 실행하지 않은 우려는 미검증 위험으로 구분한다. 추측을 버그로 확정하거나 재현하지 못한 보안/운영 위험을 검증 완료로 바꾸지 않는다. 확인된 오류가 없다는 결론도 허용하며 결과를 만들지 않는다.
- 수정 후에는 원래 재현과 영향받는 사례를 다시 확인한다. 검토만 요청받았다면 수정은 수행하지 않고 근거·영향·수정 제안을 전달한다.

## 실패를 좁히기

1. 오류와 입력·실행 조건을 보존하고 재현한다.
2. 최근 변경과 경계를 따라 실패 위치를 좁힌다. 한 가설을 하나의 관찰로 확인한다.
3. 원인에 대응하는 최소 수정을 한 뒤 원래 사례와 영향받는 회귀를 재검증한다.
4. 같은 실패를 추측 수정으로 반복하면 가설을 다시 점검한다. 플랫폼 장애와 본인 프로세스/코드 오류를 구분한다.

## 근거와 상태

- 결과를 읽고 PASS / FAIL / NOT_RUN / SKIP / HUMAN_CHECK(사용자 직접 확인 대기)를 구분한다. 테스트가 없거나 전부 skip이면 ‘검증 완료’가 아니다. 사용자가 실제 확인한 뒤에만 HUMAN_CHECK를 관측 결과로 갱신한다.
- 명령·기대값·실제 결과·종료 코드·검증한 버전/변경 상태를 기록한다. 변경 뒤 이전 실행 결과를 그대로 최신 근거로 쓰지 않는다.
- 이전 근거는 코드·입력/설정·명령·환경이 같다는 것을 확인할 수 있을 때만 재사용한다. Git commit만 같아도 추적하지 않는 데이터·설정이 바뀌었으면 근거가 달라진다. 코드/입력은 commit·diff 또는 필요한 파일 해시로 연결하고 원시 민감값은 문서에 옮기지 않는다.
- 관련 검증이 통과했다면 새 변경이나 구체적인 우려가 없는 한 반복 실행을 늘리지 않는다.
- UI 검증은 환경에서 허용된 자동화 검사, 사용자의 수동 확인, API/단위 테스트를 구분한다. 도구 사용·데이터 접근 범위는 현재 프로젝트 정책을 따른다.
- 사용자 이해·검증 구간에서는 사용자가 기대 결과를 먼저 정하고 실제 결과와 대조하도록 지원한다. probe.md의 기능별 검증·한계와 사용자 확인 범위를 갱신하고, 명령·실패·수정·재확인 이력은 devlog.md에 남긴다. 두 문서가 실제 코드와 어긋나면 해당 기능만 바로잡는다.

## 인계 직전

합의한 산출물·위치·저장 상태, 실행/운영 방법, 문서/코드 일치, 사용 자료의 출처·권한, 미구현/미검증과 사용자 영향을 확인한다. 파일 목록만으로 실제 기능의 인계를 완료했다고 판단하지 않는다. 담당자에게 확인할 항목·운영 한계·후속 범위·다음 검증을 명시하고 인계 후 수정은 버전과 관련 검증 기록으로 관리한다.

CSV 인계이 요구되면 `scripts/check_submission.py`로 확인한 계약만 검사할 수 있다. `--sample`은 열 순서를 비교하고, `--match-rows`를 함께 줬을 때만 샘플 행 수도 비교한다. `--rows`는 명시한 행 수, `--id-column`은 샘플과 ID 문자열·순서 및 유일성을 검사한다. `--required-column`은 지정 열의 빈 값을 검사한다. 샘플의 첫 열을 ID로 추정하지 않으며, 예시 몇 행을 전체 행 수 계약으로 오해하지 않는다. 다른 인계 형식에는 적용하지 않는다.

마지막 점검에서 결론이 틀릴 만한 이유를 한두 개 골라 기존 근거가 다루는지 확인한다. 빠진 중요한 반례만 실행하고, 최초 실행 소요시간을 반영해 인계 전에 끝낸다. 이미 유효한 근거가 있는 검사를 횟수만 늘려 반복하지 않는다.

반환: 무엇을 테스트했는지와 입력·기대/실제 결과·판정·한계를 연결한 표, 확인 가능한 실행/통과/실패/생략 집계, 테스트 코드/명령·근거 위치, 실패 영향·다음 조치. 예상한 오류 거절의 성공과 검사 자체의 실패를 구분하며 실행하지 않은 검사를 통과로 쓰지 않는다.
