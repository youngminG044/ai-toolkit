# 사용자가 이해할 수 있는 테스트 설명

검증 실행과 결과 인계 때 읽는다. 사용자는 코드를 처음 읽는다는 전제로, 테스트가 어떤 업무상 잘못을 잡는지와 실제 관측을 설명한다. ‘테스트 N개 통과’만으로 보고를 마치지 않는다.

## 실행 전 짧은 안내

같은 목적의 검사 묶음마다 채팅에서 다음을 알린다. 통상 검사의 실행 승인을 반복 요청하지 않는다.

- 무엇을 왜 확인하는가: 연결 기능/업무 규칙과 실패하면 사용자에게 생기는 문제.
- 어떻게 확인하는가: 대표 입력/조건, 기대 결과와 그 근거, 자동 검사/HTTP/수동 확인 중 방법.
- 어느 범위인가: 함수 하나·여러 모듈 연결·UI 흐름·정적 형식/빌드 중 실제 범위, 예상 소요와 중요한 미확인.

## 실제 결과를 읽고 설명

테스트 파일·케이스/매개변수와 실행 출력을 대조한다. 케이스가 무엇을 검증하는지는 실제 준비 데이터·호출·assert(기대와 실제를 비교하는 코드)를 읽어 판단한다. 명령 이름·종료 코드만 보고 실행된 사례나 수치를 추정하지 않는다.

사용자에게 다음 표로 현재 결과를 보여준다. 상세 값이 길면 표에는 핵심만 쓰고 같은 문서의 상세 구획을 연결한다.

| 테스트·관련 기능 | 무엇을 확인했나·입력/조건 | 기대 결과·근거 | 실제 결과 | 판정·확인한 범위/한계 |
| --- | --- | --- | --- | --- |

핵심 입력·기대값·실제값과 이유를 구체적으로 적는다. 실제 출력이 없는 값은 케이스의 assertion이 확인한 범위를 설명하되 측정 로그처럼 꾸미지 않는다. 업무상 상태 코드/단위/개수가 무엇을 뜻하는지 풀어 쓴다. 로그 전체를 채팅에 붙이지 않는다.

**설명용 예시이며 실행 근거가 아님:** ‘빈 제목을 저장하지 않음 / 공백 제목 입력 / 입력 오류로 거절하고 저장하지 않아야 함 / 아직 미실행 / NOT_RUN’. 나중에 실행했을 때 실제 확인한 응답·저장 상태만 결과에 적는다.

잘못된 입력을 거절하거나 예상한 예외를 잡았다면 그 테스트는 성공할 수 있다. 반대로 예상 밖 예외 때문에 검사가 멈췄다면 실패/실행 오류다. 제품의 오류 응답과 테스트 자체의 실패를 혼동하지 않게 설명한다.

## 상태와 집계

- PASS(통과): 실제 관측이 기대 조건을 만족했다. 확인한 입력·환경의 범위로 한정한다.
- FAIL(실패): 기대와 실제가 다르다. 어긋난 값·영향·다음 조치를 설명한다.
- TIMEOUT / ERROR: 시간 초과 / 실행 준비나 실행 중 오류. 정확성을 확인하지 못한 이유와 영향을 적는다.
- NOT_RUN / SKIP: 미실행 / 건너뜀. 각각 이유를 밝힌다. HUMAN_CHECK는 사용자 직접 확인 대기이며 통과 건수에 넣지 않는다.

실행 도구가 주는 상태를 원문 근거와 함께 유지한다. 테스트 프레임워크가 검사를 성공 처리했어도 내부에서 생략된 사례가 있으면 별도 표시한다. 실행/통과/실패/건너뜀 개수는 출력에서 확인 가능한 경우에만 보고하고 불명확하면 미확인으로 둔다. 같은 케이스의 수정 전·후 실행, 전체 검사와 그 부분집합을 중복 합산하지 않는다.

명령 종료 성공, 빌드/형식 검사, 업무 테스트, 실제 UI·사용자 확인을 구분한다. 빌드 통과를 버튼 동작·업무 정확성·전체화면 유지 확인으로 설명하지 않는다. 테스트가 없거나 모두 생략된 실행을 검증 완료로 표시하지 않는다.

## 읽을 위치와 기록

- SERVICE.md가 있으면 검증 구획에 현재 업무 테스트의 목적별 목록과 실제 `파일:테스트 함수/케이스`를 연결한다. 케이스가 많으면 목적별 요약 뒤 같은 문서의 상세 목록으로 연결하고, 어떤 사례를 포함했는지 빠뜨리지 않는다. 의존 라이브러리의 내부 테스트까지 복제하지 않는다.
- probe.md에는 기능별 핵심 입력·기대/실제 결과·판정·남은 위험과 상세 위치를 요약한다. 비서비스 업무는 허용된 기록 문서에 같은 내용을 둔다.
- devlog.md에는 실제 시각·명령/절차·검사한 버전/변경 상태·환경·결과·실패/수정/재확인 사건을 남긴다. 실패를 통과로 덮어쓰지 않고 현재 결과와 과거 사건을 구분한다.
- 기존 기록·업무 README를 보존하고 테스트 설명을 위한 별도 기록 파일을 기본 생성하지 않는다. `run_checks.py` JSON은 명령의 종료/출력 근거이며, 사례 의미와 수용 기준 해석은 Codex가 실제 코드/출력을 읽고 작성한다.

## 테스트 코드 읽기 지원

새로 작성하거나 의미 있게 변경한 핵심 테스트에는 쉬운 한국어 이름/주석으로 목적, 준비 입력, 실행 동작, 기대값의 이유를 설명한다. 작은 입력의 결과를 사용자가 먼저 예상하고 assertion과 실제 실행 결과를 함께 읽는다. 자기 구현을 복제한 기대값이나 근거 없는 수치를 정답으로 만들지 않는다.

기본 180분 집중 세션에서는 설명 가능한 검증·기록을 T+120분 전에 준비한다. 마지막 60분에는 기존 결과와 테스트 코드를 이해하며, 보고 형식을 채우려고 새 검사를 대량 실행하거나 자동 수정하지 않는다. 전체화면 유지가 필요한 환경의 수동 검사는 허용된 준비 공간에서만 진행한다.
