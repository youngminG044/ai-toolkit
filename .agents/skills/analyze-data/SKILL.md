# 데이터와 숫자의 근거

새 업무에서는 읽기 전용 표본·스키마·품질 점검 뒤 구현 전 브리핑과 사용자 확인을 먼저 마친다. 답변 반영·분석/인계 결과물의 형태와 사용 흐름, 처리·집계/분할·기준선/모델·지표·대안/장단점·위험/검증·시간을 자세히 설명하고 확인을 기다린다. 업무 답변만으로 결과 변환·모델 학습·새 분석 코드를 시작하지 않는다. 이미 확인받은 같은 계획의 실험·검증은 계속한다. solve-task가 사용 가능하면 그 스킬의 `references/implementation-brief.md`를 상세 기준으로 읽고, 선택 설치로 없더라도 이 확인 절차는 유지한다.

1. 파일·컬럼·행의 의미·단위·기준 시점·키를 파악한다. 원본을 보존하고 처음부터 전체 내용을 출력하지 않는다. CSV의 첫 점검에는 `scripts/profile_csv.py`를 사용할 수 있다.
2. 결측·중복·파싱 실패·키 조인 손실·유효 범위·시간 순서를 확인한다. 프로파일은 업무 규칙 검증과 다르다. 이상치 제거는 근거와 영향을 확인한 뒤 한다.
3. 집계는 분모·기간·필터·가중치·중복 처리 기준을 먼저 정한다. 통화·시간대·비율과 절대량을 혼동하지 않는다. 중요한 계산은 작은 수작업 사례와 대조한다.
4. ML이면 예측하는 시점 이후 생기는 컬럼과 같은 개체의 중복으로 인한 누수를 확인한다. 실제 사용과 맞는 시간/개체/무작위 분할을 선택하고 이유를 남긴다. 시간 데이터라는 이유만으로 모든 목적에 시간 분할을 강제하지 않는다.
5. 단순 규칙·평균/다수 클래스 등 의미 있는 기준선을 먼저 구한다. 목표·운영 비용에 맞는 지표를 쓰고 임계값은 검증 데이터에서 결정한다. 테스트 구간을 보고 반복 튜닝하지 않는다.
6. 표본 수·결측 제외 수·분할·기준선·개선 폭·중요한 불확실성을 함께 보고한다. 검증하지 않은 인과·일반화·성능을 주장하지 않는다.
7. 결과의 핵심 값이 실제 데이터와 코드에서 다시 계산되는지 확인하고, 사용자 결정에 주는 의미와 한계를 연결한다.

업무의 의사결정 시점·데이터 규모·실행 비용·마감을 기준으로 기준선과 핵심 분석 경로의 인계 일정을 제안한다. 사용자가 분모·분할·계산 코드와 업무 해석을 검토할 시간을 포함한다. probe.md의 해당 기능에는 전처리·분할·모델/집계·지표 선택과 같은 목적의 대안, 각 장단점·현재 제약·선택 결론을 실제 근거로 기록한다. 실험·결과·실패와 수정은 devlog.md에 남긴다.

기본 180분 집중 세션은 T+60분 1차 분석/구현·대표 검증 인계(지연 시 T+80분), T+60~120분 보완/수정+코드 이해, T+120~180분 변경 없는 코드 이해로 나눈다. 마지막 60분에는 전처리·분할·계산/모델 코드나 설정을 바꾸거나 새 튜닝/장시간 실험을 시작하지 않는다. 현재 입력·분모·함수·기존 결과를 추적해 이해를 지원하고 개선은 후보로 남긴다. 사용자 명시 수정 요청이나 다른 기간 지시가 있으면 그 영향과 범위를 먼저 설명한다.

패키지는 현재 환경에 있는 것을 먼저 사용한다. pandas·scikit-learn·DuckDB 등의 도입은 실제 필요·버전·시간·허용 범위를 확인한 뒤 결정한다. 외부 API/모델을 사용할 때는 조직의 데이터 전송·인증 정책을 확인하고 필요한 최소 데이터만 허용 범위에서 처리한다.

실행형 기준선이 필요하면 키트의 `data` 프로필을 사용한다. `data/analysis.py`는 CSV 품질·집계, `train.py`는 전처리 Pipeline과 분류/회귀·Dummy 비교, `predict.py`는 로컬 추론, `forecast.py`는 시간순 계절 naive 기준선이다. 설치된 코드와 의존성을 읽고 실제 열·타깃·분할·지표로 바꾼다. ID·예측 시점 이후 열은 명시적으로 제외하고, 시계열 입력은 한 개체·시간순·일정 간격인지 확인한다. 기준선이 실행된 사실만으로 최적 모델을 찾았거나 업무 목표를 충족했다고 판단하지 않는다.

출력: 데이터 계약, 중요 품질 문제, 재현 가능한 계산/평가, 핵심 결과와 해석, 한계. 업무가 요구한 형식과 파일명이 우선이다.
