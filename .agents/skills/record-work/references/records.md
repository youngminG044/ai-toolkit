# 두 문서의 작성 기준

두 기록 문서는 실제 사건과 판단 근거를 관리한다. 서비스의 현재 컴포넌트 관계·다이어그램·상세 API/운영 명세는 별도 SERVICE.md에 유지하고, probe에 핵심 요약과 상세 위치를 연결한다. 업무 설명 README는 보존한다.

## devlog: 사건 단위로 추가

```markdown
### T+분 / 실제 시각과 시간대 — 사건 제목
- 목적·관련 기능 ID:
- 현재 단계·관련 질문/사용자 결정: 실제 받은 답변·출처 / 열린 질문·대기 / 판단 변화
- 구현 전 브리핑: 계획 ID/버전·제안/수정·사용자 실제 확인/대기·확인 범위와 시간 영향
- 변경: 파일·함수 / 무엇이 달라졌나
- 판단: 선택과 근거 / 검토한 대안
- AI 제안·작성 / 사용자 본인 판단: 실제 제안·직접 확인·유지/수정·재확인 / 사용자 수행 근거 또는 확인 대기
- 검증 목적: 무엇을 왜 검사하는가·연결 기능/규칙·실제 테스트 파일:케이스
- 검증: 명령·입력·기대 결과와 근거·실제 결과·종료 코드·확인한 범위·근거 위치
- 상태: PASS / FAIL / TIMEOUT / ERROR / NOT_RUN / SKIP / HUMAN_CHECK
- 변경 기준: commit 또는 관련 파일 해시·변경 상태
- 사용자 확인: 직접 실행·설명한 내용 / 아직 확인하지 않은 내용
- 다음 행동·남은 한계:
```

사건이 없으면 양식을 채우기 위해 이력을 만들지 않는다. 일어난 실패는 이후 고쳤어도 사실로 보존한다. 사용자의 설명은 실제로 들은 내용만 요약한다.

## probe: 문제에서 해결과 구현까지의 현행 설명

분석 단계부터 다음 구획을 채운다. 아직 답이나 코드가 없으면 미확인·가설·미구현으로 표시한다.

probe 앞부분에는 아래 근거를 찾는 짧은 지도를 둔다. 세부 설명을 복제하거나 예상 답변을 작성하는 대신 실제 구획·기능 ID·결정 ID·devlog 사건을 가리킨다. 알고리즘·백그라운드 작업 등 해당하지 않는 것은 그 사실을 표시한다.

| 찾을 내용 | 연결할 실제 근거 |
| --- | --- |
| 핵심 동작과 확인 | 기능·입출력·정상/경계 입력·기대값/실제값 |
| 테스트 설명과 현재 결과 | 목적·입력·기대/실제값·판정·한계·테스트 코드/상세 위치 |
| AI 제안과 본인 판단 | 실제 제안·사용자 검토·유지/수정·재확인·미확인 |
| 문제 정의와 요구 확인 | 역할·페인·원인/근거·질문·답변·반영 |
| 기술 선택과 대안 | 선택/대안·각 장단점·현재 제약·선택 이유 |
| 코드 흐름과 예외 | 입력→처리→출력의 파일/함수·분기·실제 사례 |
| 한계와 다음 검증 | 미구현/미검증·사용자 영향·우선순위·확인 방법 |
| 판정 기준과 조건 변화 | 강제 조건/목표·실제 식/우선순위·얻고 포기한 점·바꾼 입력/지표 |
| 모듈 계약과 독립 검사 | 단계별 데이터·라우팅·생성/검사 의존 관계·외부 가정 |
| 작업 수명과 환경 호환성 | 중복/실패/재시작·결과 게시·전체화면 관련 코드 점검/관측 |

```markdown
## 문제 정의와 사용자
- 문제 상황·업무 목표·범위·근거:
- 페르소나: 실제 역할·목표·내리는 결정·업무 환경과 제약
- 현재 업무 흐름:

## PR01 — 실제 문제 이름
- 대상 페르소나와 발생 상황:
- 페인포인트·빈도·영향과 근거:
- 현상과 구분한 원인:
- 원인 근거와 상태: 자료 / 담당자 설명 / 관측 / 가설 / 미확인
- 해결 원리·개선할 업무 흐름:
- 원인에 어떻게 작용하는가 / 증상 완화에 그치는가:
- 연결 요구·기능(F01 등)·코드 위치:
- 업무 성공 기준·현재값/목표값·측정 위치:
- 실제 확인 결과·남은 한계:

## 질문과 사용자 판단
- 담당자 질문: 질문 ID·그대로 보낼 질문·확인 이유·우선순위·구현 영향
- 확인한 답변: 실제 답변·출처·충돌·남은 질문·반영 내용
- 사용자 판단: 결정 ID·선택지/추천/장단점·사용자 결정/대기·영향

## AI 제안과 사용자 본인 검토
- 실제 제안/작성한 내용과 관련 기능·결정:
- 사용자 본인이 확인한 요구·코드·입력·관측 결과와 그 근거:
- 채택/수정 요청/기각·이유와 실행 결과/환경 제약 근거·재확인 / 아직 사용자 확인 대기:
- 재현 입력·기대/실제 증상·AI에 실제 전달한 내용·원인 가설:
- 별도 필수 협업 문서가 있다면 실제 사건 위치:
- 해당 devlog 사건:

## 구현 전 상세 브리핑과 계획 확인
- 계획 ID·버전·현재 상태: 제안/사용자 확인 대기/확인됨/수정 확인 대기
- 답변 반영·제안 결과물과 사용 시나리오·기능별 동작/예외·수용 사례:
- 설계/데이터 흐름·추천 기술/대안/장단점·변경 예정 위치:
- 구현 전 검토·검증 계획·예상 시간/인계 영향:
- 사용자에게 실제 설명한 시점·실제 응답·확인 범위·남은 요청:
- 구현 후 계획과 달라진 내용·설명/재확인·실제 검증 근거:

## 실행·접속·API 안내
- SERVICE.md의 실제 위치·현재 작성 상태·구조/관계·주요 규칙/검증 핵심:
- 실제 실행 명령·화면 포트/경로·서버 유지 방법:
- 상태 경로와 검사 범위 / API 목록·문서·스키마의 실제 포트/경로:
- 주요 API의 메서드·역할 / 문서 공개 범위·선택 이유·실제 확인 상태:

```

페르소나는 근거 있는 업무 역할을 중심으로 작성한다. 담당자 설명을 검증된 인과로 바꾸거나 미측정 개선율을 만들지 않는다. 해결 원리는 “React 사용” 같은 도구명이 아니라 어떤 업무 구조를 바꿔 어떤 문제를 줄이는지 설명한다.

## probe: 기능별 구현과 기술 선택

```markdown
## F01 — 실제 기능 이름
- 대상 페르소나·연결 문제(PR01 등)·원인과 해결 원리:
- 요구와 사용자:
- 입력 → 처리 → 출력:
- 구현 위치와 현재 상태:
- 사용 도구·라이브러리·버전 확인 근거:

| 방법 | 장점 | 단점 | 현재 제약에서의 적용 조건 | 확인 근거/미측정 |
| --- | --- | --- | --- | --- |
| 현재 선택 | | | | |
| 현실적인 대안 | | | | |

### 선택 결론
이 요구·제약 때문에 선택한 이유, 감수한 한계, 대안으로 바꿀 조건.

### 코드와 검증
읽을 파일·함수 순서, 중요한 규칙, 실제 테스트 파일:케이스와 무엇을 왜 확인하는지,
대표·경계 입력, 기대값/근거·실제 결과·판정·한계, 명령과 devlog 사건/로그 위치.
probe의 현재 결과 표와 SERVICE의 목적별 전체 테스트 목록/상세 위치를 연결한다.
실행 전/후 사용자에게 쉬운 한국어로 설명하며 개수/기술 로그만 보고하지 않는다.

### 관련 있는 설계·운영 판단
강제 조건/선호 목표·식/우선순위/단위·근거·해 없음 처리·대안 대비 얻고 포기한 점.
화면/서버 라우팅·단계별 모듈 계약·중간 데이터·독립 검사의 공유 로직과 가정.
백그라운드 실행 위치·중복/실패/재시작·결과 게시, 조건 변화의 입력/지표·관측/미측정.
한국어 주석·SERVICE의 실제 코드 읽는 지도, 전체화면 등 환경 호환성 점검/관측 위치.
해당되지 않는 기술·실행하지 않은 사례를 채워 넣지 않는다.

### 업무 효과
기술 동작 검사와 업무 효과 측정을 구분한다. 실제 기준값·목표값·측정 결과 또는 미측정을 기록하고,
기능이 어떤 문제/원인을 다루고 무엇이 여전히 남았는지 설명한다.

### 사용자 이해 확인
입력 하나의 결과 예측 → 코드 추적 → 직접 실행·대조 → 본인 설명.
현재 상태: 확인 대기 / 일부 확인 / 확인됨. 근거와 확인 범위를 기록.
```

대안은 서로 다른 이름을 나열하는 대신 **같은 기능을 실제로 어떻게 구현하는지** 설명한다. 예: SQL은 데이터 적재·질의·집계로, Python은 파일 읽기·순회·사전 집계로 같은 결과를 만들 수 있다는 식이다. 미구현 대안이 실행·측정된 것처럼 쓰지 않는다.

기능 목록은 현재 구현을 빠짐없이 다루되, 세부 선택은 판단이 달라지는 수준에서 묶는다. 같은 공통 의존성을 여러 기능이 사용하면 공통 결정 ID를 참조하고 기능별로 달라지는 이유만 추가한다.

AI 제안·사용자 검토·유지/수정 사례가 없으면 만들어 채우지 않는다. AI가 수행한 검사를 사용자 본인이 했다고 바꾸지 않으며 사용자 보고만 있으면 그 출처를 표시한다. 한계는 사용자 영향→우선 개선→다음 검증 입력/절차·기대 결과로 연결한다.
