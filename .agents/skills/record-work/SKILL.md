# 개발 이력과 기능별 판단 근거

`devlog.md`는 실제로 일어난 일의 시간순 기록, `probe.md`는 **누가 어떤 문제를 겪고, 그 원인을 어떤 방식으로 해결하며, 현재 코드가 왜 그렇게 구현됐는지**를 연결하는 현행 문서다. 두 파일은 **업무 프로젝트 폴더**에 생성·유지한다. 배포 키트의 기록을 복사하거나 공개 키트에 실제 업무 기록을 업로드하지 않는다.

solve-task로 시작한 작업에서는 이 스킬을 다시 호출하라고 요구하지 않는다. 요구 확정·구현/선택 변경·검증·인계 및 작업 턴 종료 전에 해당 기능의 기록을 직접 갱신한다. 감시 도구의 파일명/해시 관측은 변경 목적이나 선택 이유를 대신하지 않는다.

구현 전 상세 브리핑도 두 문서에서 관리한다. probe.md에 계획 ID/버전·제안 결과물/기능/설계/대안/검증/시간·확인 상태와 범위를, devlog.md에 실제 브리핑·수정·사용자 확인 사건을 남긴다. 담당자 답변 수신과 사용자의 구현 계획 확인을 구분하고 제안/확인 대기/확인됨/구현됨/검증됨을 혼동하지 않는다. 실제 사용자 응답 없이 확인됨으로 표시하지 않는다. 이미 있는 문서에는 구획만 보완하고 별도 세 번째 계획 파일을 기본 생성하지 않는다.

## 생성

1. 업무 루트·README·기존 문서와 파일명 제한을 먼저 확인한다. 기본 설치의 `--apply`는 실제 업무 폴더에 두 기록 파일을 만든다. 없으면 `python3 <이 스킬 경로>/scripts/init_records.py --root <실제 업무 루트>`로 생성한다. 기존 파일은 그대로 보존하며 `.toolkit-package`가 있는 배포 폴더 내부에는 생성하지 않는다.
2. 업무가 다른 필수 문서를 지정하면 그 문서도 충족한다. 추가 파일을 명시적으로 금지한 경우 동일 내용을 허용된 문서의 두 구획으로 관리하고 사용자에게 위치를 알린다.
3. 생성된 양식은 근거가 아니다. 실제 요구·현재 코드·실행 결과로 채우고, 아직 없는 정보는 미구현/미확인으로 둔다. `references/records.md`의 작성 기준을 따른다.

서비스를 구현하면 업무 설명 README.md/readme.md를 보존하고 실제 업무 폴더의 SERVICE.md를 별도로 생성·갱신한다. 이 파일은 추가 계획 파일이 아니라 현재 서비스의 기술 설명서다. 컴포넌트 관계·Mermaid 아키텍처/대표 흐름·API 명세·업무/운영 규칙과 근거·실행·검증·효과/한계를 기록한다. build-service가 있으면 그 스킬의 `references/service-document.md`와 양식을 읽는다. 기존 SERVICE.md는 보존·보완하며 추가 문서 제한이 있으면 허용 위치를 확인한다. 초기 기록 도구는 두 기록 파일만 준비하며 서비스 문서 내용은 실제 서비스 작업 중 Codex가 작성한다.

## devlog.md

- 실제 변경·실험·검증·실패·복구·판단 변경 뒤에 해당 사건을 덧붙인다. 매 도구 호출마다 쓰지 않는다.
- 시각과 기준 시간대 또는 업무 경과시간, 목적, 변경 파일/함수, 한 일, 이유, 검증 명령·결과·근거 파일, 한계·다음 행동을 남긴다.
- 현재 지점은 commit 또는 관련 파일 내용의 해시/변경 상태로 연결한다. 원시 로그는 필요한 위치만 참조한다.
- 나중에 과거 내용을 재구성했다면 ‘사후 정리’와 근거를 표시한다. 원래 기록을 검증 성공처럼 바꾸지 말고 정정 이력을 덧붙인다.
- 사용자에게 코드 읽기·실행을 안내한 사실과 사용자가 직접 설명/검증한 사실을 구분한다. 사용자 확인이 없으면 이해 완료라고 쓰지 않는다.
- 테스트는 목적·관련 기능/규칙·입력·기대값/근거·실제 결과·판정·한계·테스트 코드/명령 위치를 쉬운 말로 남긴다. probe.md의 ‘테스트 설명과 현재 결과’와 SERVICE.md 상세 목록을 연결하고 실행 전/후에도 사용자에게 설명한다. 실패/시간 초과/실행 오류·미실행·생략·사용자 확인 대기를 구분하며 같은 사례의 재실행을 새 테스트 수로 합산하지 않는다.
- 담당자에게 제안한 질문, 사용자가 전달한 실제 답변·출처, 답변 때문에 바뀐 판단과 사용자 결정·대기도 이력에 남긴다. 대기 중임을 구현 진행 중이라고 쓰지 않는다.
- 중요한 AI 제안·작성 내용과 사용자 본인의 검토·유지/수정 판단을 구분한다. 사용자가 직접 수행한 확인은 실제 보고·관찰 근거와 함께 기록하고, AI가 대신 실행하거나 설명한 것을 사용자 행동으로 바꾸지 않는다. 수정이 없으면 검토 후 유지 또는 사용자 미확인 상태를 그대로 남긴다.
- 버그는 재현 조건·기대/실제 증상, AI에 전달한 내용, 원인 가설/수정안, 채택·수정 요청·기각과 각 근거, 실제 변경·재확인으로 연결한다. 기각한 제안이 없으면 만들어 채우지 않는다. 업무가 별도 AI 협업 문서를 요구하면 그 파일도 유지하고 실제 사건 위치를 연결한다.

## probe.md: 문제·페르소나·원인과 해결

기능별 설명에는 해당되는 경우 강제 조건과 선호 목표·실제 식/우선순위·단위/근거·대안 대비 얻고 포기한 점, 단계별 모듈/입출력 계약과 읽을 코드, 독립 검사/공유 로직/가정의 경계, 백그라운드 중복·실패·재시작과 결과 게시 정책, 설정/분포 변화의 입력·지표·관측을 포함한다. 관련 없는 기술을 넣지 않고 SERVICE.md 상세 위치와 devlog 사건을 연결한다. 전체화면 등 환경 호환성은 정적 점검과 실제 환경 관측/확인 대기를 구분한다.

코드 작성 전부터 아래 내용을 채우고 답변·결정이 들어오면 갱신한다. 기존 문서에 없으면 해당 구획을 보완하되 사용자가 작성한 내용을 덮어쓰지 않는다.

- 문제 상황과 업무 목표·범위·제약 및 근거.
- 페르소나의 실제 역할·업무 목표·판단·사용 상황과 현재 업무 흐름. 제공 자료에 없는 인물 설정을 만들지 않는다.
- 페인포인트의 발생 상황·빈도·영향. 수치 근거가 없으면 미확인으로 둔다.
- 현상과 구분한 원인, 담당자 설명·자료·관측·가설·미확인의 상태와 근거. 진술만으로 인과가 입증됐다고 하지 않는다.
- 해결 원리와 개선할 업무 흐름, 원인에 작용하는 방식 또는 증상 완화에 그치는 한계.
- 담당자 질문·확인 이유·답변/출처·구현 영향과 열린 질문, 사용자 판단의 선택지·추천·결정·영향.
- 문제 ID(PR01 등) → 관련 기능/요구 → 코드 위치 → 수용 기준과 검증을 연결한다. 사용하지 않는 예시 기능을 해결 근거에 넣지 않는다.
- 기술 검증과 업무 효과를 구분한다. 현재값·목표값·측정 위치와 실제 결과를 제시하고, 미측정 개선율·절감 시간·원인 제거는 주장하지 않는다.

## probe.md: 현재 구현의 기능별 전체 근거

먼저 기능 목록을 실제 사용자 동작·계산·입출력 경로와 대조한다. 의미 있는 기능마다 F01 등 ID를 붙이고 아래 내용을 빠짐없이 작성한다. 사용하지 않는 라이브러리와 사소한 문법 선택을 모두 나열하지 않는다.

1. 대상 페르소나·관련 문제 ID·원인/해결 원리, 해결하는 요구와 관찰 가능한 입력→처리→출력.
2. 현재 구현 위치(파일·함수, 확인한 경우 줄), 현재 상태와 관련 요구 ID.
3. 실제 사용한 도구·라이브러리·실행 환경, 선택 이유. 표준 라이브러리/직접 구현도 명시한다. 외부 의존성은 확인된 버전과 그 근거를 적고 버전 미확인은 구분한다.
4. 같은 요구를 달성하는 현실적인 대안. 의미 있는 대안을 보통 1~2개 선택하고 더 있다면 판단을 바꿀 것만 추가한다. 대안이 없는 지정 기술은 ‘업무 지정’과 이유를 적는다.
5. **선택안과 각 대안의 장점·단점·이 업무에서의 적용 조건**을 같은 기준으로 비교한다. 구현 시간·의존성·정확성·성능·설명 가능성·운영 제약 중 실제로 중요한 축을 사용한다. 측정하지 않은 시간·성능은 추정/미측정으로 표시한다.
6. 최종 선택의 결론: 이 업무의 어떤 제약 때문에 장단점을 감수했는지, 포기한 것, 대안으로 바꿔야 할 조건.
7. 실제 검증: 대표 사례와 기대값·실제값, 실패/경계 사례, 실행 명령·근거, 미검증 범위.
8. 사용자가 직접 볼 코드 순서와 핵심 질문, **사용자 확인 여부**. 확인 전에는 대기 상태로 둔다.

큰 기술 선택은 브리핑과 사용자 계획 확인에서 기록하고 합의한 범위를 구현한다. 인계 시 기능 목록과 핵심 선택·검증 근거를 갖추고, 사용자가 읽는 코드와 함께 설명을 보강한다. 구현/기술이 바뀌면 해당 기능의 현행 설명을 바꾸고 변경 이유는 devlog에 남긴다. 일정은 현재 업무의 범위·견적·마감과 담당자 검토 시간에 맞춘다.

기본 180분 세션의 현재 구간과 실제 경과 근거, T+60분 1차 인계/T+80분 지연 대안, T+120분 변경 중단을 기록한다. T+120분 전에 SERVICE/probe/devlog를 현재 코드와 맞추고 미완성·미검증을 표시한다. T+120~180분에는 코드 이해에 직접 필요한 짧은 확인 메모만 남기고 새 문서 확장이나 미작성 구획 채우기로 이해 시간을 사용하지 않는다. 별도 후속 문항은 실제 안내가 있을 때만 조건을 기록하며 업무 진행과 혼동하지 않는다.

## 두 문서로 근거 찾기

probe.md 앞부분에 핵심 동작/확인, AI 제안/사용자 판단, 문제/요구 확인, 기술/대안, 코드 흐름/예외, 한계/다음 검증의 **근거 지도**를 둔다. 각 항목은 해당 기능·결정·코드·devlog 사건을 가리킨다. 실제 코드·실행 근거와 대조하고 담당자 검토·사용자 직접 확인이 이루어진 범위만 확인 상태에 반영한다.

서버/API가 있으면 probe.md에 실제 실행 명령·화면/상태/문서의 포트·경로, 주요 API의 역할, 문서 공개 범위와 검증 상태를 요약한다. 상세 실행 문서가 따로 있더라도 두 기록 문서에서 핵심 접속 정보와 그 위치를 찾을 수 있게 한다. 서버 없는 업무는 해당 없음으로 두고 불필요한 API를 만들지 않는다.

SERVICE.md가 있으면 probe.md에 서비스 구조·컴포넌트 관계·주요 규칙/검증의 핵심과 상세 문서 위치를 연결한다. 구조/상세 API 계약은 SERVICE.md, 문제/선택 이유와 대안/검증 핵심은 probe.md, 시간순 사건은 devlog.md에서 유지한다. 긴 표·다이어그램을 반복 복제하지 않으며 두 기록 문서만 읽어도 핵심 판단과 근거를 찾을 수 있게 한다.

한계에는 사용자 영향·개선 우선순위·다음 확인 방법·기대 결과를 연결한다. 두 문서에서 핵심 근거를 찾되 사용자가 대표 입력을 직접 예측하고 코드 추적·실행으로 대조할 수 있도록 안내한다.

## 인계와 점검

페르소나·페인포인트·원인/근거 ↔ 해결 원리 ↔ 기능 목록 ↔ 실제 진입점·주요 모듈 ↔ 선택한 직접 의존성 ↔ 검증 항목을 대조해 누락을 찾는다. 삭제된 기능은 현행 구현에서 빼고 이력으로 남긴다. 문서 분량이나 문서 존재만으로 기능 동작·담당자 동의·공유된 이해를 확인했다고 하지 않는다.

사용자가 읽고 있는 파일은 알리지 않고 고치지 않는다. 수정이 필요하면 위치·이유·영향을 알리고 새 diff로 확인하게 한다. 조직·프로젝트에서 정한 문서 접근·AI 도구·기밀 처리 정책을 지킨다.
