# 업무 이해·구현·검토와 인계

현재 업무의 사용자·목표·운영 맥락·수용 기준을 출발점으로 삼는다. 담당자와 사실·업무 규칙·우선순위를 확인하고, 실제로 사용할 수 있는 결과물과 검증 근거·운영 한계를 공유한다.

## 구현 전 결과물을 예상할 수 있게 설명

문제 분석→담당자 질문→답변 반영 뒤 [상세 구현 브리핑](../.agents/skills/solve-task/references/implementation-brief.md)을 제시하고 사용자 계획 확인을 기다린다.

1. 확인한 문제·규칙이 어떤 사용자 흐름과 결과물로 이어지는가.
2. 화면/파일의 모습과 기능별 입력·처리·출력·예외·필수/제외 범위.
3. 데이터 흐름·모듈/파일 책임·주요 API/저장 또는 분석/모델 구조.
4. 추천 기술과 같은 목적의 대안, 각 장단점·선택 이유·감수할 한계.
5. 중요한 위험과 정상/경계/실패 검증 계획, 구현 순서·예상 소요·인계/리뷰 일정.

계획은 probe.md의 브리핑 구획, 실제 설명·수정·사용자 확인은 devlog.md 사건으로 연결한다. 내부 계획 작성이나 담당자 답변 수신을 사용자 설계 확인으로 취급하지 않는다.

## 업무별 일정 계획

사용자가 지정한 기본 집중 세션은 180분이다. 업무를 담당자와 협업해 해결하는 관점은 유지하면서 다음 구간을 적용한다. 다른 기간이나 마감을 명시하면 적용 범위와 이해 시간에 주는 영향을 설명하고 조정한다.

| 경과 | 목적 | 작업 경계 |
| --- | --- | --- |
| 0~60분 | 문제 분석·담당자 질문/답변·상세 브리핑/계획 확인·1차 구현·대표 검증 | 필수 기능과 읽을 자료를 인계할 수 있게 준비 |
| 60~120분 | 디벨롭·수정/보완과 코드 이해 병행 | 변경 위치/이유/영향을 먼저 설명하고 T+120분 전에 관련 검증·문서 정합 마무리 |
| 120~180분 | 온전히 코드 이해 | 기능·리팩터링·자동 버그 수정 중단. 구조·흐름·규칙·선택 이유·기존 결과 대조와 설명에 집중 |

지연 시 1차 인계 목표를 80분으로 조정할 수 있다. 이 경우 보완/이해 병행 구간은 80~120분의 40분으로 줄이고, 마지막 이해 구간은 120~180분으로 유지한다. 기능이 미완성이어도 이 시간을 임의로 개발에 사용하지 않는다. 사용자 명시 수정 요청이 생기면 시간 영향을 먼저 설명하고 요청 범위만 다룬다.

담당자 응답과 계획 확인 대기는 실제 경과시간에 포함한다. 범위·오류·의존성이 바뀌면 남은 시간과 마감/검토 영향을 갱신한다. 미완성·미검증 상태와 사용자 영향은 그대로 알린다.

## 코드와 업무 결과 인계에 포함할 것

1. 필수 요구별 구현·검증 상태와 실제 업무 규칙 반영 여부.
2. 실행 명령·관측한 실행 시간·대표 입력/출력·현재 코드의 변경 상태.
3. SERVICE.md의 컴포넌트 관계·아키텍처/대표 흐름·API·업무/운영 규칙·근거·검증/효과.
4. probe.md의 문제·페르소나·원인/근거·해결 원리, 선택안/대안과 읽을 파일·함수 순서.
5. devlog.md의 주요 결정·실패/수정·검증 근거와 합의한 계획 대비 변경.
6. 실행/저장·접근 정책·알려진 한계·미해결 사항·담당자와 다음으로 확인할 내용.

## 기능 하나를 함께 이해하고 검증

SERVICE.md의 유스케이스·유저플로우·아키텍처·화면/API 라우팅·모듈 입출력 계약을 연결해 읽는다. 대표 입력의 실제 중간 값과 반환값을 따라갈 순서를 제공하고 핵심 파일/함수·분기·수식·비동기 상태에 상세한 한국어 주석을 준비한다. 필요한 문법/용어도 처음 등장할 때 풀어서 설명한다. [코드 이해 기준](../.agents/skills/build-service/references/code-understanding.md)을 따른다.

설계 이해에는 해당 기능의 강제 조건/선호 목표·실제 판정 순서·대안 대비 이득/손해, 생성과 독립 검사의 경계, 백그라운드 중복/실패/재시작 정책, 조건 변화의 입력/지표도 포함한다. 구현하지 않은 큐/복구·실행하지 않은 실험을 사실로 쓰지 않는다. AI 협업은 실제 증상 전달→원인 가설/수정안→채택/수정 요청/기각의 근거→재확인을 연결한다.

| 사용자·담당자 행동 | 에이전트가 지원할 것 | 기록할 근거 |
| --- | --- | --- |
| 누가 왜 사용하는지 설명 | 사용자 역할→페인→원인/근거→해결 원리→기능 연결 | 자료·담당자 답변·가설의 구분 |
| 대표 입력의 결과 예측 | 업무 규칙과 입력 의미 안내 | 실제 예상과 근거 |
| 진입점부터 출력까지 코드 읽기 | 컴포넌트·핵심 함수·API/저장 관계 설명 | 실제 위치·남은 질문 |
| 현재 선택과 대안 비교 | 같은 기능을 만드는 방식·장단점·현재 제약 설명 | 기술 결정과 미측정 조건 |
| 직접 실행·독립 계산·UI 확인 | 재현 절차와 중요한 정상/경계/실패 사례 제공 | 기대값·실제값·검증 상태 |
| 운영 조건과 변경 영향 논의 | 현재 처리와 한계·다음 검증 제안 | 확인한 범위·후속 결정 |

검토 중인 코드에 중요한 변경이 필요하면 위치·이유·영향을 먼저 설명한다. 합의한 계획과 실제 결과물의 차이를 보여주고 관련 검증을 갱신한다. 에이전트가 설명문을 쓴 것만으로 사용자가 이해하거나 담당자가 동의했다고 기록하지 않는다.

이 변경·재검증은 기본 세션의 T+120분 전까지 진행한다. 마지막 60분에는 코드·설정·테스트를 수정하지 않고 현재 버전으로 설명한다. 새 오류나 개선점은 수정 후보로 남기며, 이해에 직접 필요한 짧은 확인 메모 외의 문서 확장도 앞 구간에서 끝낸다. 실제 제출/인계 절차가 별도로 있으면 준비를 앞당기고 필요한 시각은 확인하되 이해 시간을 몰래 줄이지 않는다.

후속 문항이 별도로 안내된 경우에는 [후속 절차 참고](../.agents/skills/solve-task/references/followup-guidance.md)를 사용한다. 6문항×5분=30분의 구성과 도구/자료 사용 조건을 보존하고 180분과의 포함 관계·현재 마감을 확인한다.

## 서비스 설명과 기록 문서의 관계

테스트를 읽을 때는 무엇을 왜 검사하는지부터 시작해 준비 입력→호출→기대값과 실제값 비교(assert)→실행 결과를 따라간다. 실행 전 목적/성공 조건, 실행 후 입력·기대/실제 결과·판정·확인 범위/한계를 채팅과 기록 문서에서 설명한다. 입력 오류를 예상대로 거절한 테스트의 성공과 검사 자체의 오류/실패를 구분한다. [테스트 설명 기준](../.agents/skills/verify-result/references/test-explanation.md)을 따른다.

SERVICE.md는 현재 업무 테스트의 목적별 전체 목록과 실제 파일:케이스·상세 결과, probe.md는 기능별 현재 결과 요약, devlog.md는 시각/명령·실패/수정·재확인 사건을 맡는다. 출력에 없는 통과/생략 개수를 만들지 않고 전체 검사와 부분 재실행도 중복 합산하지 않는다. 빌드 성공으로 실제 UI·업무 정확성·전체화면 유지까지 확인했다고 하지 않는다.

- SERVICE.md는 제공된 요구사항 README를 보존하면서 별도로 작성하는 현재 서비스 기술 설명서다. 컴포넌트·다이어그램·API/운영 명세·근거·검증·효과를 코드와 연결한다. [작성 기준과 양식](../.agents/skills/build-service/references/service-document.md)을 따른다.
- probe.md는 문제와 현재 해결 방식의 연결이다. 담당자 질의응답·사용자 판단·합의 계획·기술 선택/대안·검증 핵심·업무 효과와 한계를 유지한다.
- devlog.md는 실제 협의·결정·변경·실행·실패·수정·검증의 사건 이력이다. 사후 정리는 근거와 함께 표시한다.
- 변경 시 해당 정본을 갱신하고 다른 문서에는 핵심 요약과 실제 위치를 연결한다. 측정한 기술 결과와 실제 업무 효과를 구분한다.
